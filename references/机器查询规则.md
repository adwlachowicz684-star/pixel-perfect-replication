# 机器查询规则（AST 规则模板与反例）

> **原则**：规则必须能回答"这条在查什么"，并且必须写出"什么看起来像但不是"。
> **不要为了命中率降低精度** —— 漏报样例要回灌规则，不是放宽规则。

---

## 一、规则五要素（缺一不可）

| 要素 | 作用 |
|---|---|
| `id` | 规则标识，进 `findings.json` 的 `rule_id` |
| `evidence_question` | 这条规则在回答什么问题（防止为了命中而命中） |
| `language` | 语言，**以官方支持清单为准，不要假设** |
| `rule.pattern` / `selector` | 匹配模式 |
| `expected_card_type` | 命中应进哪类卡片（功能卡 / 证据卡 / BUG 卡 / 数据层字段） |
| `counter_example` | 反例：什么看起来像但实质不是 |

---

## 二、规则模板

```yaml
id: struct_field
evidence_question: 这个结构体有哪些 pub 字段？（用于 config 双向差集，防止漏抓 Option 字段）
language: rust
expected_card_type: 数据层字段
rule:
  pattern: 'struct $NAME { $$$FIELDS }'
  constraints:
    FIELDS:
      regex: 'pub\s+\w+\s*:'
counter_example: |
  1. 局部变量 `pub:` 不在 struct 内 —— 用 pattern 的 struct 上下文排除
  2. 同名不同对象（如两个模块各有一个 Config）—— 需按文件路径人工区分
  3. 宏生成的结构体（如 derive 展开）—— AST 可能看不到展开后字段，需补运行时证据
```

```yaml
id: command_definition
evidence_question: 有哪些 Tauri 命令定义？（用于 C1 命令存在性检查）
language: rust
expected_card_type: 功能卡 + 契约
rule:
  pattern: |
    #[tauri::command($$$ATTR)]
    pub $ASYNC fn $NAME($$$PARAMS) { $$$BODY }
  constraints:
    ASYNC: { regex: 'async|' }
counter_example: |
  1. 注释里的示例代码 —— AST 会跳过注释，但正则不会 → 这正是不用正则的理由
  2. 测试替身里定义的同名命令 —— 需按文件路径排除 tests/
  3. 字符串字面量里的 "#[tauri::command]" —— 文档字符串中的示例
```

```yaml
id: dto_property
evidence_question: TS interface 有哪些字段？（用于 C4 DTO 一致性）
language: typescript
expected_card_type: 契约
rule:
  pattern: 'interface $NAME { $$$FIELDS }'
counter_example: |
  1. type 别名而非 interface —— 需另一条规则覆盖
  2. 继承来的字段（extends）—— 展开后才是完整字段集
```

## 三、三态输出与 near_miss 抽样

脚本输出三态：

| 态 | 含义 |
|---|---|
| `matched` | 结构匹配且上下文符合 |
| `near_miss` | **结构匹配但上下文不符**（如注释里的示例、测试替身） |
| `excluded` | 被规则明确排除 |

**`near_miss` 是规则质量的体温计**，要人工每周抽样。
若 `near_miss` 持续靠"再加一层正则"修补 → 说明该升级为 CST 节点约束。

---

## 四、首次运行的三件事

1. 统计命中数、漏报样例、解析失败文件
2. **漏报样例回灌规则**（补 pattern 或 constraints）
3. 解析失败文件登记进台账「机器可解析」字段，**不许自动关闭 unknown**

---

## 五、⚠️ 语言支持的诚实边界

**ast-grep 官方支持 Rust、TypeScript、TSX、YAML 等。**
**C# 是否稳定内置支持，必须查官方实时清单** —— 不能凭一次检索快照承诺。

| 语言 | 处理 |
|---|---|
| 已支持 | 用 L2 ast-grep |
| 未支持 | 走 L3 comby（结构线索）或 L0 人工阅读 |
| 混合 | 分语言各自走不同层，结果统一进 `findings.json` |

**降级必须如实标注**：`confidence: low`，不许假装是 AST 级证据。

## 六、脚本降级行为（诚实报告）

`scripts/ast_query.py` 在 ast-grep **未安装**时：
- 退出码 **2**，明确打印"未安装 ast-grep，结果降级为正则，**confidence=low**"
- **不会假装成功**，也**不会静默跳过**（静默跳过 = 假绿灯）

## 七、实证：正则降级会命中注释里的假目标 ⭐

同一份源码（含一行注释示例 `// 注释里的示例: pub struct FakeStruct { pub x: u8 }`）：

| 引擎 | 命中 |
|---|---|
| ast-grep（AST） | 2 条（真结构体） |
| 正则降级 | **3 条** —— 多出的正是注释里的 `FakeStruct` |

**这正好印证 `counter_example` 里写的那一条**：正则分不出注释与代码，AST 能。
所以降级结果**必须人工复核**，不能当作 AST 级证据。

**⚠️ 顺带实证的工具身份陷阱**：`which sg` 会命中 Unix 的 `sg`（set group ID）命令，
它有可执行权限但没有 `scan` 子命令 —— 若只查"命令存在"，
会得到**永远 0 命中却显示成功**的假工具。脚本已做双重校验。
