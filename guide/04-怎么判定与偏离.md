# 怎么判定与偏离：怎么定性质，怎么才算"有意识地改"

## 一、四分类判定流程

```
问：去掉它，体验或正确性会受损吗？
   是 → must-match
   否 ↓
问：换实现但行为能保持不变吗？
   是 → may-evolve
   否 ↓
问：动的是模块边界而非单点吗？
   是 → should-reinvent
   否 ↓
问：需要产品/业务裁决吗？
   是 → 需要讨论（**必须带超时默认动作**）
   否 → explicit-new
```

## 二、🔑 关键区分：原样复刻 vs 考虑优化 vs 架构性调整

| 判定 | 含义 | 例子 |
|---|---|---|
| **原样复刻** | 行为与实现都不动 | 跨栏拖到空白=换栏移动 |
| **考虑优化** | 换实现，**行为不变** | 名称校验三处重复 → 合并 |
| **架构性调整** | 动模块边界 | 配置读写散落 7 处 → 统一入口 |
| **需要讨论** | 需要业务裁决 | 启动弹更新提示要不要保留 |

## 三、🔑「需要讨论」必须写全四栏

1. 卡在哪
2. 谁拍板
3. 截止时间
4. **超时默认动作**（**默认按"原样复刻"**）

> **为什么默认是"原样复刻"**：漏做是**确定的功能缺失**，
> 而多做一个没人用的功能代价低。

## 四、偏离的正确姿势

```
① 先有原版记录（没记录，不存在"偏离"，只存在"不知道"）
② 写清偏离了什么、为什么
③ 定分类
④ 找 owner + 到期日
⑤ 评估影响：哪些既有玩法 / 社区习惯 / 速通路线会被改
⑥ 记录并进台账
```

## 五、🔑 二次创作的空间在哪

> ✅ 在 `may-evolve` / `should-reinvent` / `explicit-new`
> ❌ **不在 `must-match`**

**`must-match` 不许以"新引擎更好"为由擅自改动** —— 那是手感回归。

想改 `must-match`，走的是**第 3 节"需要讨论"**流程，不是直接改。

## 六、证据等级怎么用

1–8 级（`references/证据等级.md`）。**7 级以上不得作为验收依据。**

> 🔑 **证据等级不是"源码一定赢"** ——
> 反编译源码描述的是**推测实现**，原版测量描述的是**目标真实行为**。
> 二者冲突先标 `evidence_conflict`，**不能直接认定原版是 bug**。
