## 零·补：体验参数的择优（可以改，但必须先知道原值）⭐

体验参数是最容易"顺手改掉"的一类——改的人往往不知道原值是多少，
改完也不知道自己改了什么。

| 性质 | 能不能改 | 要求 |
|---|---|---|
| **等比迁移** | 照搬 | 写"等比迁移"即可 |
| **需缩放** | 改，但要有公式 | 记下换算公式（如 13px × DPR/96） |
| **平台惯例** | 改，按新平台 | 记录原值 + 新旧惯例差异 |
| **技术权宜** | ⭐ 换成更好的 | 说清当年为什么受限 |
| **有意变更** | 改 | 登记 + golden 标 `intentional-change` |

**三条硬要求**：

1. **原值栏不许空** —— 不知道原值就回去测，不许填"未知"
2. **差异理由不许写"优化"** —— 说不清为什么就按原值，或进 unknown
3. **时序与阈值类改动要格外谨慎** —— 它们直接决定手感，
   且**用户能感觉到但说不出**（改错了很难归因）

**实证提醒**：XAML 的 Margin 是「左,上,右,下」，CSS 是「上 右 下 左」。
迁移时若照抄数值，四个方向会整体错位——**这是参数迁移里最典型的静默错误**。

### 一条专门给文案的：不许"重写得更清楚"

**文案是唯一一类"改得更好反而是错的"的东西。**
把「名称不合法，请重新输入」改成「名称格式有误」——
看上去更简洁，**但用户的肌肉记忆认的是原句**，换了措辞等于换了入口。

| 情况 | 处置 |
|---|---|
| 原文案没问题 | **照搬**，一个字都别动 |
| 确实要改（术语统一、错别字） | 登记为**有意变更**，写清改了什么、为什么 |
| 新版已经改了 | `text_extract.py` 会标为**疑似改写**，逐条判定 |

**⚠️ 尤其错误提示文案**：丢一条 = 用户遇到问题时不知道发生了什么。

| 问 | 指向 | 产出 |

| **Q1 统一管理？** | 这类操作是不是该有一个统一入口 / 统一状态？ | 消除 N 处各自为政 |

| **Q4 能否更优？** | 原版是不是受限于当年技术？ | 避免照抄技术债 |
| **Q5 值得保留吗？** ⭐ | 原版这里是不是做得很好？好在哪？ | 防止复刻时把优点搞丢 |

## 二、手法 I1：统一管理识别（Q1）

| 信号 | 表现 | 收敛方向 |
|---|---|---|
| N 处读-改-写同一份数据 | `load → mutate → save` 散落多处 | 统一 `withConfig(fn)` 事务 |
| N 处判断同一个状态 | 各处自己写 `if (locked)` | 统一 `canWrite(path)` |
| N 处弹同一类对话框 | 每个组件自己拼 Modal | 统一 `<Dialog>` / `useConfirm()` |
| N 处同样的错误处理 | 各自 `try/catch + toast + log` | 统一 `runAction()` |
| N 套取同一配置 | `data_dir_of` / `resolve_data_dir` / `data_dir` | 收敛为一个 |

**实证**：

| # | 现象 | 收敛方案 |
|---|---|---|
| I-1 ✅已修 | 名称校验 3 处重复且不一致（sys.rs 有 `.`/`..`+长度检查，mod.rs 两处没有） | 合并 `validate_name()` → **真 bug**：新建被拒的名字能靠改名写进去 |
| I-2 | 三套 data_dir 获取并存 | 收敛 `store::data_dir(app, state)` |
| I-3 | `with_config` 22 处使用，仍有 16 处直接 `load_config` | 逐个确认只读还是读-改-写，后者收敛进事务 |
| I-4 | 前端 8 个组件各自用 Modal | 统一 `useDialog()` / `<AppDialog>` |
| I-5 | 保存+toast+log 三段式重复 | 统一 `runAction(name, fn)` |

## 三、手法 I2：方法复用识别（Q2）

**识别信号**：同一正则/校验在多文件出现；相似函数名（`resolve_x`/`get_x`/`find_x`）；
复制粘贴痕迹（连注释都一样）。

| # | 重复 | 复用方案 |
|---|---|---|
| I-6 | `normalize_key` 已被 7 个文件使用 | ⭐ **已是正面样板**，继续用它，别各写各的 |
| I-7 | 前端 `openPath` 三种模式各自 catch | 统一 `safeOpen()` |
| I-8 | 图标/颜色/链接三面板的"应用到当前卡片" | 统一 `useApplyToTarget()` |
| I-9 | 各类"打开目录"按钮 | 统一 `openDir(kind)` + 目录枚举 |

## 四、手法 I3：结构化四化

| 化 | 做法 |
|---|---|
| **统一入口** | 同一类操作只有一个入口（`with_config` / `runAction` / `openDir`） |
| **统一状态** | 同一份状态只有一处真源 |
| **统一错误** | 错误只在一处定义、一处提示 |
| **统一命名** | 同一个概念只有一个名字 + 跨端别名配置 |

**判断"更规整"的标准**：新增一个同类功能时只需改一处。
需要改三处 = 还没收敛到位。

## 五、整合的时机判断 ⚠️

| 情况 | 建议 |
|---|---|
| 重复且**已经产生 bug**（如 I-1） | **立即修**，不管是否在做该功能 |
| 重复但**即将大改**（如拖拽 35 项要重写） | **跟着重写一起做**，不要先整合再重写 |
| 重复但**稳定且无 bug** | 记入清单，**等功能补完再统一重构** |

**理由**：功能未补齐时先重构，会同时面对"功能缺失"和"重构引入的回归"两类问题，
排查成本翻倍。**先补功能（在整合设计指导下），再统一重构。**

**但"优秀思路保留"要立刻做** —— 一旦重写时丢掉，就再也想不起来当初为什么那么写了。

## 六、合并的证明义务 ⚠️

**重复实现应在"统一接缝之后"整合，而不是在理解阶段提前重构。**

先把重复逻辑分别追到原入口、事件与数据字段，确认它们**确实语义相同**。
合并时必须证明以下全部等价：

- [ ] 调用前置条件
- [ ] 权限判定
- [ ] 异常处理
- [ ] 幂等性
- [ ] 重试策略
- [ ] 缓存行为
- [ ] 可观测性（日志/埋点）

**若只是代码结构相似但业务语义不同，合并会制造隐性 bug** →
保留为并行实现并**注明差异**。

## 七、反向清单：防止越复刻越倒退 ⭐

**复刻时注意力都在"原版有什么我没有"，很容易顺手把"我有原版没有"的也对齐删掉。**

**实证 12 项反向差异**：非阻塞 accept、代次号防竞态、`backup_dir` 字段等。

**做法**：
1. 从双向差集里把"当前有、原版无"的全部捞出
2. 逐条判断：真增强，还是原版不需要 / 不适用
3. 真增强的打 **勿删** 标记，写进方案文档顶部
4. **每次改到相关代码，先回头看一眼反向清单**

## 八、不适用清单

平台/架构差异导致不适用的项（实证 22 项：无边框窗口、Dispatcher、COM、stdio 特有），
**做之前先确认，别照着清单把不该搬的搬过来**。

- [ ] 每处重复实现都有明确处置（合并 / 保留并注明差异 / 延后）
- [ ] 所有 merge 都完成了证明义务清单
- [ ] 反向清单已建，勿删项已标注
- [ ] 不适用清单已建
- [ ] 每个待重写模块的 `⭐保留` 项已抄到方案文档顶部
- [ ] 整合时机已判断（立即修 / 跟着重写 / 补完再重构）
- [ ] **每个体验参数 P-N 都有性质判定**，原值栏不为空、差异理由不写"优化"
- [ ] **功能对照表五类处置已填全**（原样复刻/考虑优化/架构性调整/需要讨论/不适用）
- [ ] **「需要讨论」项四栏齐全**：卡在哪 / 谁拍板 / 截止时间 / 超时默认动作
- [ ] 无「原版✅新版❌却标完成」的危险组合
- [ ] 架构性调整项已附**重组前后对照 + 每个原入口的新落点**
- [ ] 对照表与功能台账**双向对账通过**（`feature_matrix.py --features ... --gate`）
- [ ] **时序/阈值类改动已复核**（手感类改动，改错了用户能感觉到但说不出）
- [ ] **文案改动已逐条判定**：默认照搬原文，改动的都登记为有意变更

## 十一、不通过怎么办

| 情况 | 处置 |
|---|---|
| 想合但证明不了等价 | 保留并行实现 + 注明差异，不要硬合 |
| 不确定是不是增强项 | 一律先标勿删，**误保留比误删代价小得多** |
| 整合与补功能冲突 | 先补功能，整合排到后面（除非已产生 bug） |
| 体验参数说不清为什么改 | **按原值**，或进 unknown；不许填"优化"了事 |
| 时序/阈值改动拿不准 | 保守：先按原值，跑起来再调；改动必须登记为有意变更 |
