# S2B · BUG 与审查发现

> **立场**：挖掘和修 BUG 是同一件事的两面。
> 读到一段代码觉得"这里不对"——那往往正是最重要的发现。
>
> **实证**：拖拽 35 个机制里，5 个直接产生 bug 的全是这样挖出来的
> （捕获丢失残留、重入、坐标取半路值、源页签记录、向上以标题为基准）。
> 三个"审查才发现"的问题（`&String` vs `&Path`、名称校验三份不一致、`save_records` 在事务外）
> **都不是"功能没实现"，而是"实现了但会出事"**。

---

## 一、为什么单独一张卡

| 不单独记 | 后果 |
|---|---|
| BUG 混在功能清单里 | 745 项里分不清哪些是"要补的"、哪些是"要修的" |
| 挖到 BUG 立刻深究 | 打断挖掘主线，台账推进停滞 |
| 挖到 BUG 只记不修 | 简单 BUG 白白拖到后面，且脱离刚读完代码的上下文 |
| 修了不登记 | **原版 BUG 也是用户体验的一部分**，不登记 = 静默改需求 |

## 二、记录：先记卡，不要当场深究

**挖到可疑处，30 秒记一张 B-N 卡，然后继续挖。**
当场深究会打断主线——上下文一旦丢了，回到挖掘状态要花十倍代价。

```text
B-N | 一句话描述 | 位置 | 类别 | 严重度 | 证据 | 状态
```

完整卡片见 `../assets/BUG与审查问题模板.md`。

## 三、类别（五类，决定处置方式）

| 类别 | 含义 | 修了是不是行为变更 | 处置 |
|---|---|---|---|
| **B1 原版 BUG** | 原实现本身就有的问题 | ⚠️ **是** —— 必须登记为有意变更 | 需批准 + golden 标注 |
| **B2 当前版 BUG** | 迁移侧已有/引入的问题 | 否 —— 修它回归到原版行为 | 直接修 |
| **B3 审查发现的风险** | "能跑但会出事"（并发竞态、数据覆盖、重入） | 视情况 | 判性质后处置 |
| **B4 迁移引入的** | 执行阶段新产生 | 否 | 立即修 |
| **B5 存疑待确认** | 看着像 BUG，但可能是设计意图 | — | **先确认，不许当 BUG 修** |

**B5 尤其重要**：实证 #515 清单标 `[险]`，核实发现代码本来就对
（只加 `+s` 不加 `+h`）。**照做反而会引入 bug。**

## 四、判定：真 BUG 还是设计意图

用 S3 的性质判定框架，但多问一句：

```
去掉/改掉它，体验或正确性会受损吗？
  ├─ 会 → 设计意图，不是 BUG（记入功能清单，preserve）
  ├─ 不会，且当前行为确实有害 → 真 BUG
  └─ 判断不了 → B5，进 unknown，不许默认当 BUG 修
```

**常见的"看着像 BUG 其实是设计"**：

| 看着像 BUG | 实际 |
|---|---|
| 拖到空白区被 `toast('请拖到...')` 拒绝 | **其实是通路**：跨栏拖到空白 = 换栏移动（#101） |
| 只加 `+s` 不加 `+h` | 加 `+h` 会让文件夹被隐藏（#515，原版踩过） |
| 双端滚动 33ms 防抖 | 防振荡，删了就两端来回微调 |
| 退出前强制落盘 | 异常退出兜底，不是冗余 |

## 五、分诊：当场修 vs 进批次

### 当场修（五条全满足）

| # | 条件 |
|---|---|
| 1 | 改动局限在**单个函数 / 单个文件** |
| 2 | 不涉及并发模型、数据格式、跨端契约 |
| 3 | 有明确可执行的验证方式 |
| 4 | 不需要重构（**不是"顺手重构"的借口**） |
| 5 | 不会打断当前文件的深挖主线 |

**当场修的行动**：直接给出**迁移后的实现方案**（新版怎么写），
写完验证、打勾、继续挖。方案要落到卡片【修复方案（新版）】栏。

### 进批次（任一命中）

- 跨多模块 / 多处调用点
- 涉锁、事务、编码、跨平台
- 需要重构才能修
- **修原版 BUG 导致的行为变更**（需 golden 批准）
- 需要新增 golden 或补证据才能验证

## 六、严重度

| 级 | 含义 | 门禁 |
|---|---|---|
| **P0 阻断** | 数据丢失 / 崩溃 / 功能不可用 | **硬阻塞，必须修完才许收工** |
| **P1 严重** | 竞态、静默覆盖、异常路径出错 | 硬阻塞 |
| **P2 一般** | 边界处理、文案、体验不一致 | 应修，不阻塞 |
| **P3 轻微** | 命名、冗余、可读性 | 记入即可 |

**`[险]` 标记**：涉及数据不可逆损失的，额外打 `[险]`，与 P0/P1 一起优先。

---

## 七、⚠️ 修原版 BUG = 有意行为变更

**这是本卡最容易出事的一点。**

原版的 BUG 也是用户当前体验的一部分。
复刻的目标是"用户原先的体验一点不丢"——
**修 BUG 意味着新版行为将与原版不一致**。

所以：

| 动作 | 要求 |
|---|---|
| 修 **B1 原版 BUG** | 必须登记为**有意行为变更**：写清改了什么、影响范围、批准人；golden 里对应项标注 `intentional-change` |
| 修 **B2/B4** | 不需要（修的是回归，目标就是回到原版行为） |
| 修 **B3** | 判断是否改变可观察行为，改变了就按 B1 处理 |

**不登记的 BUG 修复，等同于静默改需求。**

**反对面也要记**：有些 BUG 决定**不修**（保持与原版一致），
也要在卡片里写明"决定保留原行为，理由：……"，防止以后重新挖出来当新发现。

## 八、审查发现（B3）的四个高发区

按此顺序扫，能抓住大多数"能跑但会出事"：

| 区 | 必问 |
|---|---|
| **并发** | 有几个进程会写这份数据？读-改-写在同一临界区吗？锁可重入吗？异常会放锁吗？ |
| **数据** | 读不出来会静默用默认值吗？是唯一副本吗？写入前有拦截吗？ |
| **跨平台** | 路径含空格？编码按 BOM 判定？会吃掉别人写的内容？属性操作有副作用？ |
| **整合** | 这段逻辑别处写过吗？三份相似实现 = 迟早漂移 |

**实证**：名称校验 3 份实现、两份不一致 →
新建时被拒绝的名字（`..`、超长名）能通过改名写进去。

## 八·补：AI 修复的自纠偏闭环

**应吸收的是把 agent 输出接回证据链，而不是把审批交给 agent。**

每个 P0/P1 修复必须填自纠偏字段（见模板）：

| 字段 | 作用 |
|---|---|
| `attempt_budget` | 尝试次数上限，**超了就升级给人**（防止无限打转） |
| `根因候选` | 逼出"为什么"，不是"改哪儿" |
| `修改文件集合` | 影响面可见 |
| `测试 delta` | 是否真的加了验证 |
| `是否引入新 unknown` | 修一个不能多一个 |
| `是否新增回归` | 跨端/类型/构建是否变红 |
| `人工复核结论` | **必须有，禁止"agent 自报已修复"直接写进台账** |

**修复优先从状态夹具和契约入手**；若只能微调表象而不能解释行为 →
说明证据仍不足，**不能关闭**。

**四道锁**（AI 生成代码的等价性校验）：

| 道 | 内容 |
|---|---|
| 1 结构化搜索锁 | 同一查询在旧端和目标端都能执行（避免只 grep 到一边） |
| 2 契约锁 | 命令、参数、DTO、异常、时序有机器可读契约 |
| 3 oracle 锁 | 差分测试 + 属性测试 + golden review |
| 4 突变锁 | 故意破坏目标端，确认测试会失败 |

**任一锁都不能替代前三者。** 特别警惕"模型看一眼 diff 说可接受"——
这是最容易破坏像素级要求的捷径。

## 十、门禁

- [ ] 每个 B 条目有类别、严重度、证据、状态
- [ ] **B5 存疑项已确认**（未确认的等同于 unknown，阻塞）
- [ ] 无 P0/P1 未修复项（`bug_triage.py --gate`）
- [ ] 当场修的简单项都写了【修复方案（新版）】并已验证
- [ ] 修 B1 原版 BUG 的，已登记为有意行为变更并在 golden 中标注
- [ ] 决定"不修"的，已写明理由

## 十一、不通过怎么办

| 情况 | 处置 |
|---|---|
| P0/P1 未修复且不属简单项 | 进批次，但**必须在收工前修完**（硬阻塞） |
| 判不出是不是 BUG | 进 unknown，**不许默认当 BUG 修** |
| 修了但没登记行为变更 | 补登记；golden diff 未批准 → 回 S7 |
| 修 BUG 需要重构 | 不许当场做 → 记入整合机会表 I-N，跟着重写一起做 |
