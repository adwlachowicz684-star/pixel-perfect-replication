# S6 · 迁移执行

> **回答**：怎么分批？没编译器怎么验证？怎么提交推送？
> **纪律**：一次只迁一个能力包，每步可回滚，验证未通过立即回退。

---

## 一、批次规划：先修风险，再补功能

### 为什么数据风险必须排在最前

功能缺口是"少了个按钮"，用户能看见、会绕开。
**数据风险是"东西悄悄没了"**，用户看不见，等发现时已不可逆。

**更关键**：数据风险会放大后续所有改动。
每加一个功能就多一次读写，只要底层有覆盖漏洞，**加的功能越多、丢得越快**。
所以第 0 批必须是纯风险修复，不掺杂任何功能。

```
第 0 批：数据风险（[险] 标记）  ← 最先，纯风险
第 1 批：[易] 小项（半天内，每天用得上）
第 2 批：[中] 模块（独立可测）
第 3 批：[难] 大件（单独排一轮，如色盘全套、Markdown 编辑器）
第 4 批：像素回归（视觉/交互细节与原版并排比对）
```

**每批内部再拆成可独立验证的小批**（0-A / 0-B / 0-C），
一个小批做完就提交推送，不让改动在手上堆积。

### 批次内执行顺序

1. **先确认是真缺口还是架构差异** —— 拿不准就先做小的，大的留到最后
2. 静态验证 → 提交 → 推送 → 远端校验
3. 遇阻就先交付已完成的，别让整批卡住

## 二、无编译环境下的静态验证 ⭐

沙箱常没有 `cargo`（或编译一次要好几分钟）。
**但不验证就交付 = 交付未验证的代码**。

### 技法 1：括号平衡（含 Rust lifetime 陷阱）

```bash
python3 scripts/brace_check.py <改动文件>
```

| 陷阱 | 不处理的后果 |
|---|---|
| `'a` lifetime 当 char 字面量 | 后续所有引号配对全乱，深度永远不对 |
| `'{'` `'\''` 这类 char 字面量 | 误判为字符串开始 |
| `\\` 转义 | 要跳过下一个字符 |
| 注释里的括号 | 必须跳过 `//` 与 `/* */` |

**基线对比法**：某文件本来就不平衡时，拿改前版本跑基线，改前改后一致 = 不是你引入的。

### 技法 2：只验证新增行

```bash
git diff HEAD -- file.rs | grep '^+' | grep -v '^+++' > /tmp/added.txt
# 统计新增行里 { 与 } 的数量（先去掉字符串和注释）
```

新增行 36/36 平衡 = 这次改动本身没问题，与文件整体是否平衡无关。

### 技法 3：符号定义 / 引用计数

```bash
python3 - <<'EOF'
import re
src = open('file.rs', encoding='utf-8', errors='replace').read()
defs = r'(?:struct|fn|const|static|enum|impl)\s+'
for n in ['foo', 'bar']:
    d = len(re.findall(defs + n + r'\b', src))
    u = len(re.findall(r'\b' + n + r'\b', src)) - d
    print(f"{n}: 定义 {d} 引用 {u}")
EOF
```

- 定义 1 引用 0 → 死代码（可能是忘接上了）
- 定义 0 引用 N → **编译必然失败**

### 技法 4：提取逻辑做等价 Python 验证

纯字符串处理逻辑（如 ini 合并）**抄成 Python 跑真实用例**，
这比读代码可靠得多——能看到实际输出。

实证 `merge_icon_line` 用 5 个用例验证：
保留其它段 / 追加新段 / 清除保留它段 / 清后删空段 / 清空后全空。

### 技法 5：故障注入

见 `S4` 第五节。**脚本第一次跑就"全绿"时，要怀疑脚本是死的。**

## 三、Rust 特定踩坑（实证）

| # | 坑 | 说明 |
|---|---|---|
| 1 | `format!` 参数重复 | `{name}` 内联捕获与 `{}` 位置参数**不要混用**，统一内联 |
| 2 | `thread_local!` 的 const 初始化 | 旧版本 Rust 用 `static X: Cell<usize> = Cell::new(0);` |
| 3 | `&String` 不会自动转 `&Path` | 用 `Path::new(&s)`；**三方合并最容易带回来** |
| 4 | 生命周期让类型难以持有 | 能持有值就别借用，多一次 clone 换类型简单 |
| 5 | 文件锁必须可重入 | `thread_local!` 记层数；`_xguard` 在前、`_depth` 在后（逆序 drop） |

## 四、三个实施案例复盘

### 案例 1：0-A 数据损坏保护

**根因**：`read_json` 吞掉一切错误

```rust
fn read_json<T>(path) -> Option<T> {
    let text = fs::read_to_string(path).ok()?;   // 读失败 → None
    serde_json::from_str(&text).ok()             // 解析失败 → None
}
```

**灾难链**：
```
config.json 损坏 → 静默返回默认值 → 下次保存用默认值整份覆盖
→ 损坏原文没了（唯一能抢救的线索）+ 用户登记没了 = 两头空，不可逆
```

**解法三层**：
1. `load_strict` 区分「文件不存在」（正常）与「读不出来」（`Corrupted`）
2. 检测到损坏 → 另存现场 `<原名>.corrupt-<时间戳>.bak`（**复制而非移动**）
3. 进程内记录，所有写入路径拦住

> **检测到损坏只是第一步，拦住后续写入才是真正保住现场的那道闸。**

**必须留的逃生口**：用户删掉损坏文件后自动放行（现场副本还在），
否则程序会永久锁死。

### 案例 2：0-B 跨进程锁

**先确认再动手**：注释说"所有写入者都在同一进程内"——**错的**，
查 `main.rs` 发现 `--mcp` 是同一 exe 的独立进程实例。

**为什么用文件锁而非 OS 命名互斥量**：
Windows `CreateMutexW` / Unix semaphore 两套语义，都超出 std，
会破坏"纯 std 跨平台"的既有设计；文件锁用 `create_new(true)`（`O_EXCL|O_CREAT`）保证原子性。

**为什么超时报错而不强抢**：
> 能占着锁 10 秒说明对方真在做事。抢过来写 = 主动制造一次覆盖冲突，
> 代价是用户登记整份丢失且不可逆。

**顺带发现**：用括号匹配逐一核对 5 处 `save_records`，
发现 `core_create_link` / `core_remove_link` **在 `with_config` 闭包外**
——直接 load→save，不走事务。正是最核心的建链/删链。

### 案例 3：0-C desktop.ini

**#521 精髓**：
```
不能"先试 UTF-8、失败再回退 UTF-16"
理由：UTF-16LE 字节流当 UTF-8 解析时几乎不报错（NUL 是合法 UTF-8）
     → 回退分支永远触发不了，乱码被写回成永久脏数据
正确：先查 BOM（FF FE → UTF-16LE），严格解析，失败就报错
```

**#508 合并而非覆盖**：desktop.ini 里可能有 `[LocalizedFileNames]`、
`[ViewState]`，整份覆盖会一次性吃掉且无提示。

**#515 核实为"已正确"**：清单标 `[险]`，核对发现只加 `+s` 从未加 `+h`。
**"清单说有、实际没有"的项，核实比照做更重要** —— 照做反而会引入 bug。
已补注释固化约束，防以后误改。

## 五、提交与推送（github.com 被拦时）

```bash
# 拉取：codeload 可用
curl -sS -o /tmp/r.tar.gz https://codeload.github.com/<owner>/<repo>/tar.gz/refs/heads/main
mkdir r && tar xzf /tmp/r.tar.gz -C r --strip-components=1
# 与本地 diff -rq 比对
```

**推之前必须拉两次比对**（多窗口并发写，拉取期间可能又有人推了）。

### 防覆盖的合并策略

1. 拉 tarball 两次，确认远端无变化
2. **以远端为基准覆盖本地**
3. 把自己的改动**先备份再还原**回去
4. 分两个 commit：sync（别人的）+ fix（自己的）
5. **推送时 base = 远端最新 sha**

### 推送后必做验证

```bash
grep -c "新增的标识符" <远端文件>     # 改动在远端
grep -c "别人加的东西" <远端文件>     # 没覆盖别人的
cd <远端目录> && node scripts/cross-end-check.mjs
```

## 六、门禁

- [ ] 括号平衡 / 符号计数 / 逻辑用例（无编译环境时）
- [ ] 前端 `tsc --noEmit` 无新增错误
- [ ] `cross-end-check.mjs --strict` 绿
- [ ] 构建通过
- [ ] 改动确实在远端；没覆盖别人的改动
- [ ] 该模块 `⭐保留` 项没被写没
- [ ] 清单已标记完成（编号固定）

## 七、执行原则

1. **拿不准就先确认，别假设** —— 两次"先确认"都避免了无用功
2. **改之前先读懂"为什么现在这么写"** —— 那是前人的踩坑记录
3. **一个改动解决一类问题，不是一处** —— 散落的补丁会互相打架
4. **交付前如实说明验证边界** —— 沙箱无 cargo 时必须明说"只做了静态核对"
5. **遇阻就先交付已完成的** —— 说清剩余部分，下一轮接着做
6. **像素级不放过** —— 每完成一个模块走一遍原版真实操作路径，
   把每处不一致记成新条目，**不要说服自己"这个无所谓"**
