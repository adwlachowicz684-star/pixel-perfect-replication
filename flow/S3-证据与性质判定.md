# S3 · 证据与性质判定

> **回答**：每条证据有多硬？这个功能是设计意图还是技术权宜？该 preserve 还是 replace？
> **为什么单独一个阶段**：性质判错，后面就会把设计意图当技术债换掉（破坏体验），
> 或把技术权宜当设计意图照抄（搬来技术债）。

---

## 一、证据等级（决定这条能不能成为迁移依据）

```
runtime-verified   > dynamic-trace > static-code > resource/declaration
                   > documentation > commit-history > assumption
```

| 等级 | 怎么来的 | 能做什么 |
|---|---|---|
| **runtime-verified** | 真跑原版观察到的 | 可直接作为 golden，最高权威 |
| **dynamic-trace** | 日志 / 抓包 / 文件变化 / 断点 | 可作依据 |
| **static-code** | 读代码推断 | 需与运行证据交叉 |
| **resource/declaration** | UI 声明、schema、资源文件 | 只能证明"承诺了什么" |
| **documentation** | README、使用说明 | **可能是旧版遗留，必须验证** |
| **commit-history** | git blame / PR / issue | 只解释"为什么"，**不能推翻当前行为** |
| **assumption** | 猜的 | ❌ **不得成为迁移决定**，必须进 unknown |

**规则**：
- 每个非平凡条目至少要有 `static-code` 级证据
- 只有 `documentation` 级证据的条目，必须先补运行或静态证据
- `assumption` 级条目**一律进 unknown 清单**，S7 门禁会阻塞

详见 `../references/证据等级.md`。

## 二、性质判定：六类

```
原版这么写
  ├─ 因为业务/体验需要？        → 【设计意图】  → preserve
  ├─ 因为当年没有更好的办法？    → 【技术权宜】  → replace
  ├─ 因为平台/环境限制？        → 【平台限制】  → preserve / defer
  ├─ 因为历史遗留又没人敢动？    → 【历史债】    → remove（确认无调用方后）
  ├─ 因为写的时候没想到？        → 【无意识坏味】→ merge / 修正
  └─ 因为这是当年最漂亮的解法？  → 【优秀实践】  → ⭐ preserve + 推广
```

| 性质 | 识别信号 | 动作 | 判错的后果 |
|---|---|---|---|
| **设计意图** | 注释写明"因为业务需要"；去掉后体验/正确性受损 | **preserve** | 当成妥协换掉 → 体验丢失 |
| **技术权宜** | 手写了一段本该由库/平台提供的能力；注释里有"暂无""只能用""手动" | **replace** | 照抄 → 搬来技术债 |
| **平台限制** | 依赖特定 OS / 运行时行为 | **preserve / defer** | 误判为权宜 → 换掉后跑不起来 |
| **历史债** | TODO / FIXME / 已废弃的兼容代码 | **remove** | 留着 → 新版继续发酵 |
| **无意识坏味** | 复制粘贴、命名混乱、边界遗漏 | **merge / 修正** | 照抄 → bug 复制一遍 |
| **优秀实践** ⭐ | 全项目唯一一套规则、有防御、有注释说明"为什么" | **preserve + 推广** | 重写时丢失 → 新版反而更差 |

### 判定口诀

> **去掉它，体验或正确性会受损吗？**
> 会 → 设计意图；不会 → 看是不是当年没得选；没得选 → 技术权宜，换掉。

### 实证分类

| 原版做法 | 性质 | 动作 |
|---|---|---|
| 跨进程命名 Mutex（真有两个进程） | 设计意图 | preserve（必须补） |
| 官方 API 优先 + 直写回退 | 设计意图 | preserve |
| 双端滚动 33ms 防抖释放（防振荡） | 设计意图 | preserve |
| 写 desktop.ini 直写（未用官方 API） | 技术权宜 | replace → 官方 API |
| 手动累加高度算列表高度 | 技术权宜 | replace → `getBoundingClientRect` 实测 |
| 自绘 ICO 转换 | 技术权宜 | replace → 成熟库（原版 A2 就是这坑） |
| 轮询目录指纹（iframe emit 不可达） | 平台限制 | preserve（可换增量指纹） |
| stdio JSON-RPC | 架构选择 | preserve，但文档必须写清 |

### 权宜之计识别对照表

**当年没有 X，所以手写；现在有 X，就该换。** 逐条对照：

| 当年手写 | 现在换成 |
|---|---|
| 自绘图标格式转换（ICO / 缩略图） | 成熟图像库 |
| 手动累加高度、手动算坐标 | `getBoundingClientRect` / `ResizeObserver` / `IntersectionObserver` |
| 手写轮询 + 全量指纹 | 原生 watch API / 增量指纹 |
| 手写 JSON 解析容错 | schema 校验（zod / serde default） |
| 手写字符串拼接路径 | `path.join` / `Path::join` |
| 手写防抖节流 | 现成 hook / 库 |
| 手写深比较 / 深拷贝 | `structuredClone` / 序列化库 |
| 手写编码探测 | 按 BOM 严格判定 + 编码库 |
| 手写状态机 if-else | 显式状态机 / reducer |
| 手写线程池 / 队列 | 语言原生 async + 任务队列 |

**⚠️ 换之前必须确认**：换成新方案后**边界行为是否一致**（错误文案、失败回退、极端输入）。
**换方案最容易丢的，就是原来那个丑实现里藏着的边界处理。**

## 三、优秀思路保留清单 ⭐（复刻中最容易丢的东西）

**复刻不是否定原版。** 那些"只有踩过坑才会这么写"的地方，
必须显式识别、单独记录、并在新版里保住——否则会出现"功能全对齐了，但更难用了"。

**识别信号**：

| 信号 | 含义 |
|---|---|
| 注释里写"**为什么**"而不只是"做了什么" | 前人踩过坑，这是踩坑记录 |
| 有防御性分支且分支里有具体业务含义 | 不是冗余，是被真实场景教育过 |
| 全项目唯一一套某类规则 | 已经收敛过的最佳实践 |
| 有回退路径（官方 API 失败 → 直写） | 考虑了现实环境的不确定性 |
| 有兜底（退出前落盘、异常时恢复） | 考虑了异常路径 |
| 有防抖 / 抑制 / 重入保护 | 考虑了真实操作节奏 |

**实证：必须保留的优秀设计**

| # | 优秀设计 | 好在哪 | 新版处理 |
|---|---|---|---|
| G-1 | `normalize_key` 全项目唯一一套路径规范化（7 文件共用） | 避免 N 套规则互相打架 | 保留并推广，不要各写各的 |
| G-2 | 官方 API 优先 + 直写回退 | 改图标即时生效；极端环境仍能写 | 保留双层，**别简化成单层** |
| G-3 | 跨进程文件锁 + 超时报错而不强抢 | 抢锁 = 主动制造覆盖冲突 | 保留"不抢锁"语义 |
| G-4 | load 与 save 在同一临界区（`with_config` 事务） | 只在写时加锁挡不住读-改-写覆盖 | 沿用事务语义 |
| G-5 | 损坏检测 + 另存现场 + 拦住后续写入 | 拦住写入才真正保住现场 | 三层一起搬 |
| G-6 | 临时摘锁 → 执行 → `finally` 恢复 | 明确的状态窗口管理 | 沿用，保证可重入 |
| G-7 | 双端滚动 33ms 防抖释放 | 防两端来回微调成振荡 | 做编辑器时必须保留 |
| G-8 | 连锁发送 400ms 防抖 | 匹配真实操作节奏 | 保留，别当冗余删掉 |
| G-9 | 只加 `+s` 不加 `+h` | 加 `+h` 会让文件夹被隐藏 | 保留 + 补注释固化约束 |
| G-10 | 退出兜底落盘 | 异常退出不丢改动 | 必须补 |

**做法**：功能清单里给这些条目打 `⭐保留`，
方案文档【保留项】栏写清"好在哪"。
**重写这些模块的人必须先读这段，再动手。**

## 四、性质判定表（产物格式）

| 编号 | 功能 | 原位置 | 证据等级 | 性质 | 动作 | 理由 | 保留要点 |
|---|---|---|---|---|---|---|---|
| #101 | 跨栏拖到空白=换栏移动 | DragService.cs:88 | runtime-verified | 设计意图 | preserve | 被当错误处理堵死 | 落点栏=目标栏当前 activeTab |
| #504 | desktop.ini 直写 | IconSvc.cs:201 | static-code | 技术权宜 | replace | 官方 API 可即时生效 | 回退路径必须保留（G-2） |

**每个非平凡条目必须有一个动作标签，没有就说明没判。**

### 四·补2：判定完立刻落到功能对照表 ⭐

性质判定表是**逐条台账**（给执行看），但项目组和验收人要看的是**总账**——
**原先有哪些功能、现在有哪些功能、每条怎么处置的、哪些还没定**。
所以每判完一批，立刻同步写 `ledger/feature_matrix.md`：

| 编号 | 功能 | 原版 | 新版 | 处置 | 依据（证据卡/性质） | 状态 |
|---|---|---|---|---|---|---|
| 1 | 跨栏拖到空白=换栏移动 | ✅ | ✅ | **原样复刻** | E-012 设计意图 | 完成 |
| 2 | 名称校验三处重复 | ✅ | ✅ | **考虑优化** | E-030 无意识坏味 → merge | 完成 |
| 3 | 配置读写散落 7 处 | ✅ | ✅ | **架构性调整** | E-041 统一入口 | 完成 |
| 4 | 启动弹更新提示 | ✅ | ❌ | **需要讨论** | 卡在哪/谁拍板/截止时间/超时默认 | 待拍板 |
| 5 | 托盘图标动画 | ✅ | ❌ | 不适用 | 平台差异 | 已裁定 |

**五类处置**与**四条判据**见 `assets/功能对照表模板.md`，
自检 `scripts/feature_matrix.py --check ... --gate`。

**❗「需要讨论」必须写全四栏**：`卡在哪 / 谁拍板 / 截止时间 / 超时默认动作`。
**超时默认按「原样复刻」** —— 漏做是确定的缺失，多做个没人用的功能代价低。

**⚠️ `原版✅新版❌` 却标「完成」是最危险的组合** —— 被当做了，实际是丢了。

## 四·补：BUG 也要过一遍性质判定

**"看着像 BUG"和"真是 BUG"是两回事。** 挖到的每个 B-N 条都要过这一层：

```
去掉/改掉它，体验或正确性会受损吗？
  ├─ 会     → 设计意图，不是 BUG → 转入功能清单，preserve
  ├─ 不会且当前行为确实有害 → 真 BUG → 按 S2B 分诊
  └─ 判不了 → B5 存疑 → 进 unknown，不许默认当 BUG 修
```

**实证**：#515 清单标 `[险]`，核实发现代码本来就对（只加 `+s` 不加 `+h`）。
**照做反而会引入 bug。**

**反之，这些"看着像 BUG"其实都是设计**：
双端滚动 33ms 防抖（防振荡）、退出前强制落盘（异常兜底）、
官方 API 失败后直写回退（环境兜底）、只加 `+s`（加 `+h` 会让文件夹消失）。

**同时，下面这些是真 BUG 且必须修**（它们不是功能缺失，是"实现了但会出事"）：

| 问题 | 怎么发现的 |
|---|---|
| `&String` vs `&Path` | diff 双方而非只看无冲突（硬编译错误） |
| 名称校验三份不一致 | 找整合机会时扫出来（真 bug：`..` 能写进去） |
| `save_records` 在事务外 | 括号匹配定位闭包范围（竞态落点） |

## 五、门禁

- [ ] 每个条目都有证据等级，无 `assumption` 级决定
- [ ] 每个非平凡条目都有动作标签（preserve/replace/merge/remove/defer）
- [ ] **每个 B-N 条都过了"真 BUG 还是设计意图"这一层**，B5 存疑项已进 unknown
- [ ] 所有 `replace` 都写清"新平台能力为何更好"+"边界行为如何等价"
- [ ] 所有 `merge` 都证明了原语义等价（前置条件/权限/异常/幂等/重试/缓存）
- [ ] 优秀设计已录入保留清单 G-N
- [ ] unknown 清单已更新（含受阻原因与所需条件）

## 六、不通过怎么办

| 情况 | 处置 |
|---|---|
| 证据只有 documentation 级 | 补运行或静态证据；补不上 → 进 unknown |
| 判不出性质 | 进 unknown，**不许默认 preserve**（默认 preserve 会把技术债全搬过来） |
| 想 merge 但证明不了等价 | 保留为并行实现并**注明差异**，不要硬合 |
| unknown 项环境受限无法验证 | 写明"环境受限"+ 所需条件，S7 会一直阻塞到清零 |
| B-N 判不出是不是真 BUG | 标 B5 进 unknown，**不许默认当 BUG 修**；修错 = 引入新 bug |
