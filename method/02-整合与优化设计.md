# 02 · 整合与优化设计：从"照抄"到"择优复刻"

> **定位**：01 回答"原版有什么"，本文件回答"**新版该怎么写**"。
>
> 只做前者会产出一份"照抄清单"，照着做完得到的是
> **把旧代码的技术债原样搬到新语言里**。
>
> **本文件与 01 同步进行**：不要等挖完再想怎么整合。
> 每挖完一个模块，立刻记录：重复出现的模式、与已挖模块重复的逻辑、
> 原版受技术限制的实现、以及**原版做得好的地方**。

---

# 第一部分 · 复刻五问 ⭐

**每挖到一项功能，除了"原版怎么做"，必须同时问这五个问题。**
前三个问"怎么组织"，后两个问"该保留还是该换掉"。

| 问 | 指向 | 产出 |
|---|---|---|
| **Q1 统一管理？** | 这类操作是不是应该有一个**统一入口 / 统一状态**？ | 消除 N 处各自为政 |
| **Q2 方法复用？** | 这段逻辑是不是已经在别处写过？ | 消除重复实现 |
| **Q3 什么性质？** | 这是**设计意图**、**技术权宜**、**平台限制**，还是**历史债**？ | 决定照做还是换掉 |
| **Q4 能否更优？** | 原版这么写是不是**受限于当时的技术**？新版能不能更好？ | 避免照抄技术债 |
| **Q5 值得保留吗？** ⭐ | 原版这里是不是**做得很好**？好在哪？怎么保住？ | 防止复刻时把优点搞丢 |

**Q3 是枢纽**：判断错了，Q4 就会把设计意图当成技术债换掉（破坏体验），
或把技术权宜当成设计意图照抄（搬来技术债）。

**Q5 最容易被忽略**：复刻时注意力都在"补缺口"，
很容易在重写的顺手之中，把原版那些**只有做过才知道为什么要这么写的巧思**一起丢掉。

# 第二部分 · 性质判定：六类归类 ⭐

```
原版这么写
  ├─ 因为业务/体验需要？        → 【设计意图】保留语义，照着做
  ├─ 因为当年没有更好的办法？    → 【技术权宜】新版换更好的方案
  ├─ 因为平台/环境限制？        → 【平台限制】看新版是否仍受限
  ├─ 因为历史遗留又没人敢动？    → 【历史债】确认无副作用后清理
  ├─ 因为写的时候没想到？        → 【无意识坏味】顺手修正
  └─ 因为这是当年最漂亮的解法？  → 【优秀实践】⭐ 保留，并写清好在哪
```

## 六类判定表

| 性质 | 识别信号 | 处理策略 | 风险 |
|---|---|---|---|
| **设计意图** | 注释写明"因为业务需要"；去掉后体验/正确性受损 | **必须补，照着语义做** | 当成妥协换掉 → 体验丢失 |
| **技术权宜** | 手写了一段本该由库/平台提供的能力；注释里有"暂无""只能用""手动" | **换成新版的成熟方案** | 照抄 → 搬来技术债 |
| **平台限制** | 依赖特定 OS / 运行时行为 | 确认新版是否仍受限；仍受限则保留，可局部优化 | 误判为权宜 → 换掉后跑不起来 |
| **历史债** | 有 TODO / FIXME / 重复分支 / 已废弃的兼容代码 | 确认无调用方后清理 | 留着 → 新版继续发酵 |
| **无意识坏味** | 复制粘贴、命名混乱、边界遗漏 | 顺手修正，记入整合表 | 照抄 → bug 复制一遍 |
| **优秀实践** ⭐ | 全项目唯一一套规则、有防御、有注释说明"为什么" | **保留并推广为统一封装** | 重写时丢失 → 新版反而更差 |

## 本例实证分类

| 原版做法 | 性质 | 新版处理 |
|---|---|---|
| 跨进程命名 Mutex | **设计意图**（真有两个进程） | ✅ 必须补（#468/469） |
| 官方 API 优先 + 直写回退 | **设计意图**（缓存由系统维护） | ✅ 必须补（#504） |
| 双端滚动 33ms 防抖释放 | **设计意图**（防振荡） | ✅ 做 MD 编辑器时必须 |
| 写 desktop.ini 直写 | **技术权宜**（未用官方 API） | ⭐ 改用官方 API |
| 手动累加高度算列表高度 | **技术权宜**（当年无测量 API） | ⭐ 用 `getBoundingClientRect` 实测（#734） |
| 自绘 ICO 转换 | **技术权宜**（当年无三方库） | ⭐ 用成熟库（原版 A2 就是这坑） |
| 轮询目录指纹 | **平台限制**（iframe 里 emit 不可达） | ⚠️ 仍受限，但可换 IndexedDB 增量 |
| stdio JSON-RPC | **架构选择** | ⚠️ 当前 HTTP 也合理，**但文档必须写清** |

## 权宜之计识别对照表（按技术演进查）

**当年没有 X，所以手写；现在有 X，就该换。** 逐条对照：

| 当年手写的东西 | 现在该换成 |
|---|---|
| 自绘图标格式转换（ICO / 缩略图） | 成熟图像库（sharp / image-rs / PIL） |
| 手动累加高度、手动算坐标 | `getBoundingClientRect` / `IntersectionObserver` / `ResizeObserver` |
| 手写轮询 + 全量指纹 | 原生 watch API / 增量指纹 / IndexedDB |
| 手写 JSON 解析容错 | 成熟 schema 校验（zod / serde with default） |
| 手写字符串拼接路径 | `path.join` / `std::path::Path::join` |
| 手写防抖节流 | 现成 hook / `debounce` 库 |
| 手写深比较 / 深拷贝 | `structuredClone` / 序列化库 |
| 手写编码探测 | 按 BOM 严格判定 + 成熟编码库 |
| 手写日期/时间差计算 | 标准库 / date 库 |
| 手写状态机 if-else | 显式状态机 / reducer |
| 手写线程池 / 队列 | 语言原生 async + 任务队列 |

**⚠️ 换之前必须确认**：换成新方案后，
**边界行为是否一致**（错误文案、失败回退、极端输入）。
换方案最容易丢的就是"原来那个丑实现里藏着的边界处理"。

# 第三部分 · 优秀思路保留清单 ⭐（复刻中最容易丢的东西）

**复刻不是否定原版。** 原版里那些"只有踩过坑才会这么写"的地方，
必须显式识别、单独记录、并在新版里保住——否则会出现"功能全对齐了，但更难用了"。

## 如何识别优秀思路

| 信号 | 含义 |
|---|---|
| 注释里写"**为什么**"而不只是"做了什么" | 前人踩过坑，这是踩坑记录 |
| 有**防御性分支**且分支里有具体业务含义 | 不是冗余，是被真实场景教育过 |
| **全项目唯一一套**某类规则 | 已经收敛过的最佳实践 |
| 有**回退路径**（官方 API 失败 → 直写） | 考虑了现实环境的不确定性 |
| 有**兜底**（退出前落盘、异常时恢复） | 考虑了异常路径 |
| 有**防抖 / 抑制 / 重入保护** | 考虑了真实操作节奏 |

## 本例实证：必须保留的优秀设计

| # | 优秀设计 | 好在哪 | 新版怎么处理 |
|---|---|---|---|
| **G-1** | `normalize_key` —— 全项目唯一一套路径规范化规则，7 个文件共用 | 避免 N 套规则互相打架 | ✅ **已是正面样板**，新版继续用它，不要各写各的 |
| **G-2** | **官方 API 优先 + 直写回退** | 缓存由系统维护，改图标即时生效；同时保证极端环境下仍能写 | 保留双层结构，别简化成单层 |
| **G-3** | **跨进程文件锁 + 超时报错而不强抢** | 能占锁 10 秒说明对方真在做事，抢锁 = 主动制造覆盖冲突 | 保留"不抢锁"的语义 |
| **G-4** | **load 与 save 在同一临界区**（`with_config` 事务） | 只在写时加锁挡不住读-改-写覆盖 | 新版沿用事务语义，别退化成分散加锁 |
| **G-5** | **损坏检测 + 另存现场 + 拦住后续写入** | 检测到只是第一步，**拦住写入**才真正保住现场 | 三层一起搬，别只搬第一层 |
| **G-6** | **临时摘锁 → 执行 → `finally` 恢复** | 明确的状态窗口管理 | 沿用，并保证可重入 |
| **G-7** | **双端滚动 33ms 防抖释放** | 防两端来回微调成振荡 | 做编辑器时必须保留 |
| **G-8** | **连锁发送 400ms 防抖** | 匹配真实操作节奏 | 保留，别当成冗余删掉 |
| **G-9** | **只加 `+s` 不加 `+h`** | 加 `+h` 会让文件夹被隐藏（原版踩过） | 保留并补注释固化约束，防以后误改 |
| **G-10** | **退出兜底落盘** | 异常退出不丢改动 | 必须补（原版 C12） |

**做法**：在功能清单里给这些条目打 `⭐保留` 标记，
并在方案文档的【性质判定】栏写清"**优秀实践 —— 好在哪**"。
**重写这些模块的人必须先读这段，再动手。**

# 第四部分 · 整合手法 I1-I5

## 手法 I1：统一管理识别（Q1）

**问法**：这类操作现在有几处各自为政？能不能收敛成一个入口？

| 信号 | 表现 | 收敛方向 |
|---|---|---|
| **N 处读-改-写同一份数据** | `load → mutate → save` 散落多处 | 统一为 `withConfig(fn)` 事务 |
| **N 处判断同一个状态** | 各处自己写 `if (locked)` | 统一为一个 `canWrite(path)` 判定 |
| **N 处弹同一类对话框** | 每个组件自己拼 Modal | 统一为一个 `<Dialog>` 或 `useConfirm()` |
| **N 处同样的错误处理** | 各自 `try/catch + toast + log` | 统一为 `runAction()` 包装 |
| **N 套取同一配置** | `data_dir_of` / `resolve_data_dir` / `data_dir` | 收敛为一个 |

**本例实证**：

| # | 现象 | 收敛方案 |
|---|---|---|
| I-1 ✅**已修** | **名称校验 3 处重复且不一致**（mod.rs 两处内联 / sys.rs 一处） | 合并为 `sys::validate_name()`；**sys.rs 有 `.`/`..`+长度检查，mod.rs 两处没有** → 真 bug：新建被拒的名字能靠改名写进去 |
| I-2 | **三套 data_dir 获取并存** | 收敛为 `store::data_dir(app, state)` 一处 |
| I-3 | `with_config` **已有 22 处使用**，但仍有 **16 处直接 `load_config`**（mod 8 / mcp 5 / backup 3） | 逐个确认是「只读」还是「读-改-写」；后者收敛进事务 |
| I-4 | **前端 8 个组件各自用 Modal** | 统一 `useDialog()` / `<AppDialog>` |
| I-5 | **保存+toast+log 三段式重复** | 统一 `runAction(name, fn)`（含错误兜底） |

## 手法 I2：方法复用识别（Q2）

**问法**：这段逻辑是不是已经在别处写过？

**识别信号**：
- 同一个正则 / 同一个校验在多文件出现
- 相似的函数名（`resolve_x` / `get_x` / `find_x`）
- 复制粘贴的痕迹（连注释都一样）

| # | 重复 | 复用方案 |
|---|---|---|
| I-6 | `normalize_key` 已在 7 个文件使用 | ✅ **已是正面样板** —— 全项目唯一一套路径规范化规则 |
| I-7 | 前端 `openPath` 三种模式各自 catch | 统一 `safeOpen()` |
| I-8 | 图标/颜色/链接三个面板的"应用到当前卡片" | 统一 `useApplyToTarget()` hook |
| I-9 | 各类"打开目录"按钮（数据/备份/项目/项目组） | 统一 `openDir(kind)` + 一个目录枚举 |

## 手法 I3：性质判定与优化识别（Q3 + Q4）

见第二部分。判据一句话：
> **去掉它，体验或正确性会受损吗？**
> 会 → 设计意图；不会 → 看是不是当年没得选；没得选 → 技术权宜，换掉。

## 手法 I4：结构化四化（让新版更规整、更能迭代）

整合不只是"去掉重复"，更是**让新结构能承接后续迭代**：

| 化 | 含义 | 做法 |
|---|---|---|
| **统一入口** | 同一类操作只有一个入口 | `with_config` / `runAction` / `openDir` |
| **统一状态** | 同一份状态只有一处真源 | 收敛为单一 store / 单一判定函数 |
| **统一错误** | 错误只在一处定义、一处提示 | 统一 `runAction()` 兜底 + 统一错误文案表 |
| **统一命名** | 同一个概念只有一个名字 | 命名表 + 跨端别名配置（见 05） |

**判断"更规整"的标准**：
新增一个同类功能时，是不是只需改一处？
如果需要改三处，说明还没收敛到位。

## 手法 I5：整合机会表（交付物模板）

每完成一个模块的挖掘，产出 / 更新这张表：

| 编号 | 类型 | 现状 | 整合方案 | 性质 | 影响面 | 优先级 |
|---|---|---|---|---|---|---|
| I-1 | 重复+不一致 | 名称校验 3 处 | 合并 `validate_name()` | 无意识坏味（含 bug） | 3 文件 | 高 |
| I-2 | 重复 | 三套 data_dir | 收敛一处 | 历史债 | 3 文件 | 中 |
| G-2 | ⭐优秀 | 官方 API + 回退 | **保留并推广** | 优秀实践 | 图标系统 | — |

**这张表与功能缺口清单并列**，是复刻的两份核心交付：
- **功能缺口清单**：要补什么（745 项）
- **整合机会表**：该怎么组织（21 处）+ 该保留什么（10 处优秀设计）

# 第五部分 · 整合的时机判断 ⚠️

**不是所有整合都该现在做。** 三条判断：

| 情况 | 建议 |
|---|---|
| 重复且**已经产生 bug**（如 I-1 校验不一致） | **立即修**，不管是否在做该功能 |
| 重复但**即将大改**（如拖拽 35 项要重写） | **跟着重写一起做**，不要先整合再重写 |
| 重复但**稳定且无 bug** | 记入清单，**等功能补完再统一重构** |

**理由**：功能未补齐时先重构，会同时面对"功能缺失"和"重构引入的回归"两类问题，
排查成本翻倍。**先补功能（在整合设计指导下），再统一重构。**

**但"优秀思路保留"要立刻做** —— 因为一旦重写时丢掉，就再也想不起来当初为什么那么写了。
在动手重写某个模块前，先把这个模块里的 `⭐保留` 项抄到方案文档顶部。

# 第六部分 · 反向清单：防止越复刻越倒退 ⭐

**复刻时注意力都在"原版有什么我没有"，很容易顺手把"我有原版没有"的也对齐删掉。**

**本例 12 项反向差异（标注勿删）**：

| 类型 | 例子 |
|---|---|
| 架构改进 | 非阻塞 accept |
| 并发改进 | 代次号防竞态 |
| 数据字段 | `backup_dir` 字段 |

**做法**：
1. 从双向差集（01 手法 7）里把"当前有、原版无"的全部捞出
2. 逐条判断：是真增强，还是原版不需要 / 不适用
3. 真增强的打 **勿删** 标记，写进方案文档顶部
4. **每次改到相关代码，先回头看一眼反向清单**
