## 一、批次规划：先修风险，再补功能

### 为什么数据风险必须排在最前

功能缺口是"少了个按钮"，用户能看见、会绕开。
**数据风险是"东西悄悄没了"**，用户看不见，等发现时已不可逆。

更关键的是：**数据风险会放大后续所有改动**。
每加一个功能就多一次读写，只要底层有覆盖漏洞，加的功能越多、丢得越快。
所以第 0 批必须是纯风险修复，不掺杂任何功能。

### 分批原则

```
第 0 批：数据风险（[险] 标记）  ← 最先做，做完再碰功能
第 1 批：[易] 小项（半天内，每天用得上）
第 2 批：[中] 模块（独立可测）
第 3 批：[难] 大件（单独排一轮，如色盘全套、Markdown 编辑器）
第 4 批：像素回归（视觉/交互细节与原版并排比对）
```

**每批内部再拆成可独立验证的小批**（如 0-A / 0-B / 0-C），
一个小批做完就提交推送，不让改动在手上堆积。

### 批次内的执行顺序

1. **先确认是真缺口还是架构差异** —— 拿不准就先做小的，大的留到最后
2. 静态验证 → 提交 → 推送 → 远端校验
3. 遇阻就先交付已完成的，别让整批卡住

## 二、无编译环境下的静态验证 ⭐ 本 Skill 最实用部分

沙箱常没有 `cargo`（或编译一次要好几分钟）。
**但不验证就交付 = 交付未验证的代码**。所以必须有静态验证手段。

### 技法 1：括号平衡检测（含 Rust 陷阱）

最直接有效的检查——能抓住绝大多数"改漏了一半个括号"。

```python
# /tmp/brace.py  —— 可复用的括号平衡器
def check(fn):
    t = open(fn, encoding='utf-8', errors='replace').read()
    depth = 0; i = 0; n = len(t); ok = True
    in_s = in_c = in_lc = in_bc = False
    while i < n:
        ch = t[i]; nxt = t[i+1] if i+1 < n else ''
        if in_lc:
            if ch == '\n': in_lc = False
            i += 1; continue
        if in_bc:
            if ch == '*' and nxt == '/': in_bc = False; i += 2; continue
            i += 1; continue
        if in_s:
            if ch == '\\': i += 2; continue
            if ch == '"': in_s = False
            i += 1; continue
        if in_c:
            if ch == '\\': i += 2; continue
            if ch == "'": in_c = False
            i += 1; continue
        if ch == '/' and nxt == '/': in_lc = True; i += 2; continue
        if ch == '/' and nxt == '*': in_bc = True; i += 2; continue
        if ch == '"': in_s = True; i += 1; continue
        if ch == "'":
            # ⚠️ 关键：区分 lifetime 与 char 字面量
            if nxt.isalpha() or nxt == '_':
                i += 1; continue          # 'a '_ 'static —— 不是字符
            in_c = True; i += 1; continue
        if ch in '{[(': depth += 1
        elif ch in '}])':
            depth -= 1
            if depth < 0: ok = False
        i += 1
    return ok and depth == 0
```

**四个必须处理的陷阱**：

| 陷阱 | 不处理的后果 |
|---|---|
| `'a` lifetime 当 char 字面量 | 后续所有引号配对全乱，深度永远不对 |
| `'{'` `'\''` 这类 char 字面量 | 误判为字符串开始 |
| `\r\n` 在字符串里 | 无影响，但 `\\` 转义要跳过下一个字符 |
| 注释里的括号 | 必须跳过 `//` 与 `/* */` |

**基线对比法**：如果某文件本来就不平衡（说明解析器或文件本身有特殊情况），
**拿改前的版本跑一遍做基线**，只要改前改后数值一致就说明不是你引入的。

```
基线 mod.rs: depth=2
本地 mod.rs: depth=2   ← 一致，改动安全
```

### 技法 2：只验证新增行

更精准的做法——只看 diff 里 `+` 行的括号是否平衡：

```bash
git diff HEAD -- file.rs | grep '^+' | grep -v '^+++' > /tmp/added.txt
# 统计新增行里 { 与 } 的数量（先去掉字符串和注释）
```

新增行 36/36 平衡 = 这次改动本身没问题，与文件整体是否平衡无关。

### 技法 3：符号定义 / 引用计数

快速确认"定义了没用"或"用了没定义"：

```python
import re
defs = r'(?:struct|fn|const|static|enum|impl)\s+'
for n in ['foo', 'bar']:
    d = len(re.findall(defs + n + r'\b', src))
    u = len(re.findall(r'\b' + n + r'\b', src)) - d
    print(f"{n}: 定义 {d} 引用 {u}")
```

- 定义 1 引用 0 → 死代码（可能是忘接上了）
- 定义 0 引用 N → **编译必然失败**（漏了定义或导入）

### 技法 4：提取逻辑做等价 Python 验证

纯字符串处理逻辑（如 ini 合并）可以**抄成 Python 跑真实用例**。
这比读代码可靠得多——能看到实际输出。

本轮 `merge_icon_line` 用 5 个用例验证：
保留其它段 / 追加新段 / 清除保留它段 / 清后删空段 / 清空后全空。

### 技法 5：故障注入（写的是校验脚本时必做）

见 04 号 Skill 第四节。核心：**脚本第一次跑就"全绿"时，要怀疑脚本是死的**。

## 三、Rust 特定踩坑（本轮实证）

### 坑 1：`format!` 参数重复

```rust
// ❌ 两个 {e} 都是内联捕获，却又传了两个位置参数 → 编译失败
format!("{e}；且{e}（...）", qe, path.display())

// ✅ 统一用内联捕获
let qe = ...; let orig = ...;
format!("{e}；且{qe}（...: {orig}）")
```

**规则**：`{name}` 内联捕获与 `{}` 位置参数**不要混用**。
混用有时能编译（旧写法），但极易写错，统一成内联最清晰。

### 坑 2：`thread_local!` 的 `const` 初始化

```rust
// ❌ 需要较新 Rust（Cell::new 非 const 时）
static X: Cell<usize> = const { Cell::new(0) };

// ✅ 兼容旧版本（本项目 rust-version = 1.77.2）
static X: Cell<usize> = Cell::new(0);
```

### 坑 3：`&String` 不会自动转 `&Path`

```rust
rename_with_fallback(old, &new_path)             // ❌ new_path 是 String
rename_with_fallback(old, Path::new(&new_path))  // ✅
```

这类错误**三方合并时最容易带回来**——对方已改好的版本被旧版本覆盖。
合并后必须 diff 双方，不能只看"没冲突"。

### 坑 4：生命周期让类型难以持有

```rust
// 想让 guard 借用 lock，结果生命周期到处报错
pub struct Guard<'a> { lock: &'a FileLock }

// ✅ 直接持有 PathBuf，生命周期消失
pub struct Guard { path: PathBuf }
```

**经验**：能持有值就别借用。多一次 clone（一个路径而已）换取类型简单，非常划算。

### 坑 5：文件锁必须可重入

`with_config` 闭包里调 `with_records`，两个都拿同一把文件锁 = **自己等自己**，死锁且无提示。

解法：`thread_local!` 记层数，外层持有则内层跳过：

```rust
fn acquire(dir) -> Result<Option<Guard>, String> {
    if LOCK_DEPTH.with(|d| d.get() > 0) {
        LOCK_DEPTH.with(|d| d.set(d.get() + 1));
        return Ok(None);           // 内层复用
    }
    let g = data_lock(dir).lock()?;
    LOCK_DEPTH.with(|d| d.set(1));
    Ok(Some(g))
}
// 配合 LockDepthGuard 在退出时 -1
// ⚠️ 声明顺序：_xguard 在前，_depth 在后 → 逆序 drop 先减层数再放锁
```

## 四、三个实施案例复盘

### 案例 1：0-A 数据损坏保护（#170 #531 #535）

**根因**：`read_json` 吞掉一切错误

```rust
fn read_json<T>(path) -> Option<T> {
    let text = fs::read_to_string(path).ok()?;   // 读失败 → None
    serde_json::from_str(&text).ok()             // 解析失败 → None
}
```

**灾难链**：
```
config.json 损坏 → 静默返回默认值 → 下次保存用默认值整份覆盖
→ 损坏原文没了（唯一能抢救的线索）+ 用户登记没了 = 两头空，不可逆
```

**解法三层**：
1. `load_strict` 区分「文件不存在」（正常）与「读不出来」（`Corrupted`）
2. 检测到损坏 → 另存现场 `<原名>.corrupt-<时间戳>.bak`（**复制而非移动**）
3. 进程内记录，所有写入路径拦住

**关键设计**：
> 检测到损坏只是第一步，**拦住后续写入**才是真正保住现场的那道闸。

**必须留的逃生口**：用户删掉损坏文件后自动放行（现场副本还在），
否则程序会永久锁死，用户除了重装没别的办法。

### 案例 2：0-B 跨进程锁（#468 #469）

**先确认再动手**：原代码注释说"所有写入者都在同一进程内，不需要文件锁"。
**这个假设是错的** —— 查 `main.rs` 发现 `--mcp` 是同一 exe 的独立进程实例。

**教训**：代码注释里的架构假设可能已过时。
**改并发模型前必须验证当前架构，而不是信注释。**

**为什么用文件锁而非 OS 命名互斥量**：
- Windows `CreateMutexW` / Unix semaphore 是两套语义不同的 API，都超出 std
- 引入后 `fsutil` 会变成平台分支的集合体，破坏"纯 std 跨平台"的既有设计
- 文件锁用 `create_new(true)`（底层 `O_EXCL|O_CREAT`）保证原子性

**为什么超时报错而不强抢**：
> 能占着锁 10 秒说明对方真在做事。抢过来写 = 主动制造一次覆盖冲突，
> 而这类冲突的代价是用户登记整份丢失且不可逆。

**顺带发现的竞态落点**：
用括号匹配逐一核对 5 处 `save_records`，发现 `core_create_link` /
`core_remove_link` **在 `with_config` 闭包外** —— 直接 load→save，不走事务。
这正是最核心的建链 / 删链功能。

### 案例 3：0-C desktop.ini（#508 #510 #521）

**#521 的精髓**（最容易理解错的一条）：
```
不能"先试 UTF-8、失败再回退 UTF-16"
理由：UTF-16LE 字节流（如 61 00 62 00）当 UTF-8 解析时几乎不报错
     —— NUL 是合法 UTF-8 字符，于是得到 "a\0b\0" 这种乱码
     回退分支永远触发不了，乱码被写回成永久脏数据
正确：先查 BOM（FF FE → UTF-16LE），严格解析，失败就报错
```

**#508 合并而非覆盖**：
desktop.ini 里可能有 `[LocalizedFileNames]`（中文别名）、`[ViewState]`（视图设置）。
整份覆盖会一次性吃掉，且无任何提示。

**#515 核实为"已正确"**：
清单标了 `[险]`，但核对代码发现只加 `+s` 从未加 `+h`。
**这类"清单说有、实际没有"的项，核实比照做更重要** ——
照做反而可能引入 bug（本来对的，改错了）。
已补注释固化约束，防以后误改。

## 五、提交与推送流程（github.com 被拦时）

本环境 `github.com` 被网络策略 403 拦截，但 `api.github.com` 可用。

### 同步远端（拉取）

```bash
# codeload 可用，用它拉 tarball
curl -sS -o /tmp/r.tar.gz \
  https://codeload.github.com/<owner>/<repo>/tar.gz/refs/heads/main
mkdir r && tar xzf /tmp/r.tar.gz -C r --strip-components=1
# 与本地 diff -rq 比对
```

**推之前必须拉两次比对** —— 这个仓库有多个窗口并发写，
拉取期间可能又有人推了。

### 防覆盖的合并策略

1. 拉 tarball 两次，确认远端无变化
2. **以远端为基准覆盖本地**
3. 把自己的改动**先备份再还原**回去
4. 分两个 commit：sync（别人的）+ fix（自己的）
5. **推送时 base = 远端最新 sha**

### 推送（Git Data API）

```
POST /git/blobs      → 文件内容
POST /git/trees      → 带 base_tree 增量建树
POST /git/commits    → 挂父提交
PATCH /git/refs/heads/main → 移指针
```

**只推自己改的文件**，不要把整个 sync commit 重放（体积大、易触发 500）。

### 推送后必做的验证

```bash
# 1. 改动在远端
grep -c "新增的标识符" 远端文件
# 2. 别人的改动没被覆盖
grep -c "别人加的东西" 远端文件
# 3. 远端能跑校验
cd 远端目录 && node cross-end-check.mjs
```

## 七、执行中的通用原则

### 原则 1：拿不准就先确认，别假设

本轮两次"先确认"都避免了无用功：
- `--mcp` 是不是独立进程 → 确认是真 bug，不是架构差异
- #515 是真缺口吗 → 确认是已正确，不用改

**反过来，一次"信了注释"就差点做错**：
代码注释说"所有写入者都在同一进程内"——实际不是。

### 原则 2：改之前先读懂"为什么现在这么写"

`with_config` 的注释详细解释了"为什么必须整体加锁而不是只在 save 时加锁"。
这种注释是**前人的踩坑记录**，改之前必须读，否则会退回到错误的做法。

### 原则 3：一个改动解决一类问题，不是一处

- 损坏保护：不是给 `load_config` 打个补丁，而是**所有写入路径统一拦**
- 跨进程锁：不是给某个命令加锁，而是**事务层统一加**

散落的补丁会互相打架，也会漏。

### 原则 4：交付前如实说明验证边界

沙箱无 cargo 时，**必须明确说"Rust 侧只做了静态核对，需要本地编译确认"**。
不能因为"看起来对"就宣称验证通过。

### 原则 5：遇阻就先交付已完成的

本轮多次在轮次上限前卡住。正确做法不是硬撑，
而是**把已完成的部分提交推送，说清剩余部分**，下一轮接着做。

### 原则 6：像素级不放过（本 Skill 强化）

功能"能跑"和"体验一致"是两件事。
每完成一个模块，走一遍原版的真实操作路径，
**把看到的每一处不一致都记成新条目**，而不是说服自己"这个无所谓"。

## 八、与 01 / 02 / 03 / 04 的接口

```
01 挖出清单 + 整合机会 + 优秀思路保留清单
        ↓
02 按批次转成改动方案（含每个改动的验收标准与⭐保留项）
        ↓
03 执行 + 静态验证 + 提交推送 + 远端校验   ← 本文件
        ↓
04 跨端契约校验（执行前后各跑一次）
```

- **执行前**跑 04：确认基线绿（别把已有问题算到自己头上）
- **执行后**跑 04：确认没引入契约漂移
- 04 报错 → 回到 02 修方案，不要在执行阶段硬改

---

*执行阶段最容易丢的不是功能，是"为什么这么改"。*
*每个数据风险改动都要写清：根因 → 灾难链 → 为什么解法能堵住它。*
*三个月后回看，只有这个能让人判断"这个改动能不能动"。*
