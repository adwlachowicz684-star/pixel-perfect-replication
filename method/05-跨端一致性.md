# 05 · 跨端一致性保障

> **体系位置**：01 挖掘与整合设计 → 02 实现方案与代码审查 → 03 执行与验收 → **04 跨端一致性保障**
>
> 04 是**最先该建的第二份** —— 因为它的需求在 01 阶段就已暴露：
> 本项目人工核对过 45 个命令的定义 / 注册 / 调用对齐、41 个命令的参数名与 Rust 签名比对，
> **全部是手工做的**。手工做一次可以，第二次必漏。

---

## 一、为什么需要这一层

跨端契约**天然分散在多个文件里**，加一个功能要同时改 N 处：

```
Rust 命令定义（mod.rs / xxx.rs）
      ↓  必须同名
Rust 命令注册（main.rs invoke_handler）
      ↓  必须同名同参
前端调用（api.ts）
      ↓  字段必须对应
前端类型（types.ts）
```

**漏改任何一处的后果**：

| 漏改 | 运行时表现 | 误导性 |
|---|---|---|
| 没注册 | `command not found` | 低（还算好查） |
| 参数名不符 | **静默传 undefined**，Rust 拿到默认值 | **高** —— 功能"时好时坏" |
| Option 与非 Option 搞反 | 前端不传 → Rust 反序列化失败 | 中 |
| DTO 少字段 | 前端读到 undefined，或**保存时被静默丢弃** | **极高** —— 数据丢失 |

**最危险的是最后一类**：前端 `saveConfig` 传整份 config，
TS 里多写的字段 Rust 不认识会被丢弃，Rust 有的字段 TS 没写就传 undefined 覆盖。
**config 是整份覆盖写回的**，一次漂移 = 用户设置静默丢失。

**本项目实证**：曾出现 `FpxConfig` 漏 `chainActions` 字段（对应 Rust `chain_actions`）——
整份 config 回传时缺失，serde 走 default 得到 null，后端判定"尚未迁移"并用内置值重置，
**用户自己加的连锁动作全没了**。

## 二、四类检查（本 Skill 的核心交付）

| # | 检查 | 抓什么 |
|---|---|---|
| **C1** | **命令存在性** | 定义了没注册 / 注册了没定义 / 前端调用了不存在的命令 |
| **C2** | **参数名一致性** | 前端传的参数名 ≠ Rust 参数名（含命名风格映射） |
| **C3** | **必填/可选匹配** | Rust 非 `Option` 的参数，前端没传 |
| **C4** | **DTO 字段一致性** | `model.rs` 结构体字段 ≠ `types.ts` interface 字段 |

### C1 命令存在性

三方比对，两个方向都要查：
```
定义集 = {#[tauri::command] 下的 pub (async) fn}
注册集 = {main.rs invoke_handler 里 fpx::xxx}
调用集 = {api.ts call<T>('xxx')}
```
- `定义集 - 注册集` → **注册缺失**（写了但没挂上，前端调用必失败）
- `注册集 - 定义集` → **定义缺失**（构建期就会报错，但早发现更好）
- `调用集 - 定义集` → **孤儿调用**（前端调了个不存在的命令）

### C2 参数名一致性 ⭐ 最容易漂移

**关键**：Rust 与 TS 的命名风格不同，比对前必须先映射。

```rust
#[tauri::command(rename_all = "snake_case")]   // TS 的 camelCase → Rust 的 snake_case
pub fn fpx_rename_folder(..., new_name: String) {}
```
```ts
call<RenameResult>('fpx_rename_folder', { kind, path, new_name: newName })
//                                                    ^^^^^^^^ 必须写 snake_case
```

**本项目约定**：`rename_all = "snake_case"` 时，**前端也写 snake_case**（`new_name`）。
所以比对时两边都按原名比，最简单也最不易错。
若改成 camelCase 风格，则比对时需做 `snakeToCamel` 转换。

**排除注入参数**：`app: AppHandle`、`state: State<...>` 是 Tauri 注入的，
**不是前端传的**，比对时必须排除，否则每个命令都会误报。

### C3 必填 / 可选匹配

```rust
target: Option<String>,   // 可选 → 前端可以不传
kind: String,             // 必填 → 前端必须传
```
判据：`/^Option\s*</.test(type)`。

**注意**：Rust 侧 `Option` 但前端**必传**是可以的（传 null 也行），
反过来**不行** —— 非 Option 而前端没传，反序列化直接失败。
所以**只查一个方向**。

### C4 DTO 字段一致性

两边字段集（Rust 转 camelCase 后）必须完全相等，少了多了都报。

**需要配置的三类例外**：
```js
STRUCT_ALIAS  = { ChainActionItem: 'ChainAction' }   // 改名过，不是错误
INTERNAL_ONLY = new Set(['LinkRecord'])              // 内部用，不暴露前端
```
`INTERNAL_ONLY` 报**提示**而非错误，避免噪音。

## 三、实现要点（踩过的坑）

### 坑 1：`[^}]*` 会提前截断 ⭐ 必踩

```python
# ❌ 错：注释里出现 } 就截断
re.finditer(r'pub struct (\w+)\s*\{([^}]*)\}', src)

# ✅ 对：大括号配对
def read_braced(src, open_idx):
    depth, j = 0, open_idx
    while j < len(src):
        if src[j] == '{': depth += 1
        elif src[j] == '}':
            depth -= 1
            if depth == 0: break
        j += 1
    return src[open_idx+1:j]
```

**实证**：本项目 `FpxConfig` 有 39 个字段，用 `[^}]*` 只抓到 33 个，
**漏掉 `chain_prompt` / `chain_actions` / `watch_enabled` / `watch_interval_secs`
/ `preset_icons` / `icon_groups` 六个** ——
而 `chain_actions` 恰恰是此前出过数据丢失 bug 的那个字段。

### 坑 2：对象字面量的简写属性

api.ts 里 `{ kind, path, new_name: newName }` 混用简写与键值对：
```js
// 简写 kind 没有冒号，只匹配 (\w+)\s*: 会漏掉
const m = /^(\w+)\s*:/.exec(k);
return { name: m ? m[1] : k, optional: false };
```

### 坑 3：`pub async fn` 别漏

正则要写 `pub (?:async )? fn`。本项目 4 个 async 命令
（`fpx_backup` / `fpx_list_editors` / `fpx_capture_screen` / `fpx_import_icons`）
第一次扫描全漏了，表现为"前端调用了 4 个不存在的命令"。

### 坑 4：多文件定义

命令不都在 `mod.rs`，DTO 也不都在 `model.rs`：
```
命令：fpx/mod.rs（47 个全部在此，但要写成 glob 防以后拆分）
DTO ：model.rs / backup.rs / screen.rs / chain.rs / watch.rs / editor.rs
```
脚本里用文件列表逐个读，`try/catch` 跳过不存在的文件。

### 坑 5：脚本要能发现"永远绿灯"

**我自己差点犯这个错**：脚本第一次跑是"✅ 全部一致"，
但这可能意味着脚本是死的。**必须用故障注入验证。**

## 四、故障注入验证（必做）⭐

写完校验脚本，**必须故意制造错误，确认能被抓到**。
否则它可能永远输出"通过"，比没有更危险——给人虚假的安全感。

**四类故障，逐一验证**：

| 故障 | 注入方式 | 期望报错 |
|---|---|---|
| F1 参数名写错 | `{ new_name: newName }` → `{ newName }` | `[参数名不符]` + `[必传参数缺失]` |
| F2 DTO 少字段 | 删掉 `linkedGroup: string \| null;` 那一行 | `[DTO 字段缺失]` |
| F3 新增必传参数 | Rust 加 `force_rebuild: bool` | `[必传参数缺失]` |
| F4 命令未注册 | main.rs 删掉 `fpx::fpx_copy_text,` | `[注册缺失]` |

**操作规范**：
```bash
# 1. 先备份
cp api.ts /tmp/api.bak && cp types.ts /tmp/types.bak
cp src-tauri/src/fpx/mod.rs /tmp/mod.bak && cp src-tauri/src/main.rs /tmp/main.bak

# 2. 注入 → 跑脚本 → 确认报错 → 还原
sed -i 's/xxx/yyy/' api.ts && node cross-end-check.mjs | grep "❌"
cp /tmp/api.bak api.ts

# 3. 最后必须确认还原
git status --short      # 应该只剩新增的脚本文件
```

**注意 sed 写法**：先用 `grep -n` 看字段的真实写法再删。
实证里我按 `linkedGroup?: string;` 去删，实际是 `linkedGroup: string | null;`，
**sed 没匹配上，误以为脚本抓不到** —— 差点冤枉了正确的脚本。

## 五、接入 CI

只写脚本不接 CI，等于没写——人不会记得手动跑。

```yaml
- name: 跨端契约一致性检查
  run: npm run crossend:check -- --strict
```

`--strict` 让有错时退出码 1，阻断合并。

**放在哪一步**：依赖只需要 node（不需要 cargo / npm install），
所以可以**放在最前面**，几十毫秒出结果，快速失败。

## 六、本项目实证结果

```
Rust 命令 47 · 注册 47 · 前端调用 48（含 1 个外壳命令）
Rust DTO 29 · TS interface 27
✅ 全部一致
```

故障注入四类全部命中，`--strict` 正确返回退出码。

**扫描过程本身的发现**（说明这层有价值）：
1. 第一次扫描漏了 4 个 `async` 命令（正则问题）
2. 第一次 DTO 提取少 6 个字段（`[^}]*` 截断问题）
3. 确认 `ChainActionItem` ↔ `ChainAction` 是**改名**而非错误（需配置别名）
4. 确认 `LinkRecord` 是内部结构体，不暴露前端（需配置排除）
5. `WindowInfo` 只在 Rust 侧，前端不需要（提示，非错误）

## 七、复用清单（换项目时改这些）

| 项 | 本项目值 | 改成你的 |
|---|---|---|
| 命令前缀 | `fpx_` | 你的前缀 |
| Rust 源目录 | `src-tauri/src/fpx/*.rs` | 你的路径 |
| 注册文件 | `src-tauri/src/main.rs` | 你的入口 |
| 注册写法 | `fpx::fpx_xxx` | 你的形式 |
| 前端调用文件 | `plugins/project-group/api.ts` | 你的路径 |
| 调用写法 | `call<T>('cmd', {...})` | 你的封装 |
| 注入参数 | `app` / `state` | 你的（如 `window` / `db`） |
| 结构体别名 | `ChainActionItem → ChainAction` | 你的改名映射 |
| 内部结构体 | `LinkRecord` | 你的 |
| DTO 文件列表 | model / backup / screen / chain / watch / editor | 你的 |

## 八、与 01 / 02 / 03 的接口

- **从 01 来**：01 挖出"命令清单"，04 保证两端不漂移
- **到 02 去**：02 做代码审查时，先跑 04，绿了再审业务逻辑
- **到 03 去**：03 验收时，04 是回归检查的一部分

**04 的产出是"防线"，不是"功能"** —— 它不增加能力，
但保证 01/02/03 加的东西不会因为契约漂移而在运行时崩掉或静默丢数据。

---

*写完脚本不验证 = 没写。写完脚本不接 CI = 慢慢失效。*
*这两条是本项目实证中最实在的两条经验。*
