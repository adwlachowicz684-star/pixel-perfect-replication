## 一、从清单到方案：四项转化

清单条目是"缺什么"，方案要回答的是：

| 清单给的是 | 方案要补的是 |
|---|---|
| 缺什么功能 | 在**哪个文件**改、改**哪几处** |
| 原版怎么做 | 当前架构下**能不能照做**（设计意图 vs 技术权宜） |
| 优先级 / 难度 | 拆成几个**可独立验证**的小批 |
| 完成标准 | 怎么**证明**它真的生效了 |
| （新增）原版这里做得好吗 | 哪些是**⭐必须保留的优秀设计** |

### 转化第一问：这是设计意图还是技术权宜？

02 号的 Q3/Q4 已给判据，这里给处理分寸：

| 性质 | 处理 |
|---|---|
| 设计意图（跨进程 Mutex、官方 API 优先、滚动防抖） | **必须补，照着语义做** |
| 技术权宜（直写 desktop.ini、手动累加高度、自绘 ICO） | ⭐ **改用更好的方案**，但边界行为要对齐 |
| 平台限制（轮询目录指纹） | 仍受限，可局部优化 |
| 优秀实践（⭐保留项） | **先抄下来再动手**，别在重写中丢掉 |

**照抄 = 把技术债搬到新语言**。这是"复刻"和"移植"的分界线。

### 转化第二问：真缺口还是架构差异？

清单里有 22 项标注"不适用"（无边框窗口、Dispatcher、COM、stdio 特有）。
**做之前先确认**，别照着清单把不该搬的搬过来。

**本轮实证**：#515 清单标 `[险]`，核实发现代码本来就对（只加 `+s` 不加 `+h`）。
**照做反而会引入 bug。**

### 转化第三问：当前有没有比原版更好的？

02 号记录了 12 项"当前有而原版没有"，标注**勿删**。
复刻时注意力都在"原版有什么我没有"，**很容易顺手把增强项也对齐删掉**。

### 转化第四问（新增）：重写会不会把优点写没了？

每个要重写的模块，方案文档顶部必须列出该模块的 `⭐保留` 项。
**重写前读一遍，写完再对照一遍。**

## 二、审查的六个观察层

按此顺序审，能抓住大多数"能跑但会出事"的问题。

### 层 1：契约层（先跑 04，绿了再审别的）

```
Rust 定义 ←→ main.rs 注册 ←→ api.ts 调用 ←→ types.ts 类型
```

**先跑 04 再审业务**：契约问题会让后续审查的结论全部失真
（参数名不对时，你看"功能对不对"是在看一个根本没传进去的参数）。

### 层 2：并发层 ⭐ 最容易漏

**必问四个问题**：

1. **有几个进程会写这份数据？**
   本轮实证：注释说"只有进程内"，实际 `--mcp` 是独立进程。
   **不要信注释，去查入口代码**。

2. **读-改-写是原子的吗？**
   ```
   A: cfg = load()        // 版本 1
   B: load → 改 → save()  // 版本 2
   A: 基于版本 1 改完 save()  // 版本 3，B 的改动整份没了
   ```
   **只在写时加锁挡不住这个** —— 必须 load 与 save 在同一临界区。

3. **锁可重入吗？**
   事务 A 的闭包里调事务 B，两把都拿同一把锁 = 自己等自己。

4. **异常路径会放锁吗？**
   用 RAII（drop 时释放），不要手动 unlock。

### 层 3：数据风险层 ⭐ 后果最重

**必问三个问题**：

1. **读不出来时会怎样？**
   静默返回默认值 → 下次保存整份覆盖 → 原文和用户数据两头空。
   **正确做法**：区分「文件不存在」与「读不出来」，后者必须中止。

2. **这是唯一副本吗？**
   没有别处兜底、没有版本号迁移 → 一次误覆盖不可逆。

3. **写入前有没有拦？**
   > 检测到损坏只是第一步，**拦住后续写入**才是真正保住现场的那道闸。

### 层 4：跨平台层

见 01 号第十部分「负面教训库」。审查时重点看：

- 路径含空格 → 加引号了吗？
- 文件编码 → BOM 判定还是"先试后回退"？（后者会静默产生乱码）
- 属性操作 → 加了 `+h` 会不会让文件消失？
- 覆盖写 → 会不会吃掉别人写的内容？

### 层 5：整合层

- 这段逻辑**是不是别处写过**？（三份相似实现 = 迟早漂移）
- 加了这个功能，要不要同步到统一入口？
- 有没有绕过已有的统一封装（如 `with_config` / `with_records`）？
- （新增）**有没有把 `⭐保留` 的优秀设计写没了？**

**本轮实证**：名称校验有 3 份实现，两份不一致 →
新建时被拒绝的名字（`..`、超长名）能通过改名写进去。

### 层 6：像素层（本 Skill 新增）⭐

**功能对了不等于体验对了。** 审查时逐项比对：

| 像素维度 | 比对什么 |
|---|---|
| 视觉 | 间距/尺寸/颜色/图标/圆角/阴影、**动效时长与缓动曲线**、hover/disabled/选中态 |
| 交互 | 手势每个阶段、阈值与死区、让位与回弹、自动滚动、异常残留是否清理 |
| 数据 | 字段集、默认值、序列化格式与命名、编码（BOM）、迁移兼容 |
| 行为 | **文案措辞原文**、错误提示、时序与防抖、失败/中断后的状态、退出兜底 |

**实操**：功能完成后，拿原版和新版并排操作一遍同样的流程，
逐步比对截图与文案。**不比对就宣称"对齐了"是不允许的。**

## 三、审查的具体手法

### 手法 R1：用括号匹配定位"是否在闭包内"

判断某行代码是否在某个事务/闭包保护下，**不能靠行号距离**：

```python
# 对 with_config 的位置做真正的括号匹配，得到闭包范围
# 再判断 save_records 的行号是否落在范围内
```

本轮用这招从 5 处 `save_records` 里揪出 2 处在闭包外——
**正是最核心的建链/删链**。

### 手法 R2：diff 双方，而非只看"没冲突"

三方合并时，对方的修复可能被旧版本覆盖回来。

本轮实证：`&String → &Path` 的修正被合并带回旧写法，
那是**硬编译错误**。只看"无冲突"发现不了。

### 手法 R3：反向验证——清单说有，实际有吗？

清单是**扫描产物**，可能有误判（如 TipsPanel 旧版遗留文案）。
核对代码后要能**作废条目并记下理由**（作废的条目也要留档）。

### 手法 R4：读真实数据文件

代码只处理它认识的字段。
当前实现"不知道有这个字段"、原版"只处理认识的字段"——
**两边看代码都正常，只有把真实数据文件打开比对才暴露差异**。

本轮：`link-record.json` 真实数据有 `clusters` 字段，
当前实现没有 → **迁移时被静默丢弃，写回时永久删除**。

### 手法 R5：故障注入验证审查工具

同 04 号第四节。审查脚本本身也要验证——**永远绿的脚本等于没有**。

### 手法 R6：像素比对审查（新增）

```text
1. 列出该功能的所有可感知点（文案 / 样式 / 时序 / 反馈）
2. 原版截图 + 新版截图并排
3. 逐项打勾，不一致的记入清单，不许用"差不多"放行
```

## 四、方案文档模板

每个改动写清楚这七项，执行时不会跑偏：

```
【编号】#101 跨栏拖到空白 = 换栏移动
【根因】原版 ResolveLinkDrop：命中卡片=建链，没命中=跨列移动。
       当前把没命中一律 toast 拒绝，通路被堵死。
【现状】后端 moveCardAcross 已完整实现（含物理搬家），前端没接上。
【性质】设计意图 —— 必须补，照着语义做
【保留项】⭐ 落点栏 = 目标栏当前 activeTab（与所见一致）—— 别改成别的栏
【改法】onCrossDrop 里 target 为 null 时调 moveCardAcross
【验证】tsc 0 错误；拖到空白后日志显示"已转为X"；像素比对：插入条位置与高亮一致
【风险】换栏可能触发物理搬家，失败时后端整体中止（已有逻辑）
```

**【现状】这一项特别重要** ——
本轮多次发现"后端早就实现了，只是前端没接"，
这类改动比想象中小得多，先摸清现状能省大量工作量。

**【保留项】是新增的必填项** ——
提醒重写的人别把原版的巧思一起改掉；没有就写"无"。

## 六、与 01 / 02 / 03 / 04 的接口

```
01 → 02：清单 + 整合机会表 + 「勿删」清单 + 「不适用」清单 + 疑问清单
02 → 03：改动方案（七项模板）+ 验收标准
02 → 04：新增/修改的命令与 DTO，供校验脚本更新别名配置
03 → 02：执行中发现的新问题，回流成新的清单条目
```

**02 是闭环的枢纽**：01 挖出来的东西要经过 02 判断"要不要做、怎么做"，
04 的契约校验结果要回到 02 修方案，03 执行中遇到的意外要回流成清单条目。

## 七、本轮实证：三个"审查才发现"的问题

| 问题 | 怎么发现的 | 性质 |
|---|---|---|
| `&String` vs `&Path` | diff 双方而非只看无冲突 | **硬编译错误** |
| 名称校验三份不一致 | 找整合机会时扫出来的 | 真 bug（`..` 能写进去） |
| `save_records` 在事务外 | 括号匹配定位闭包范围 | 竞态落点 |

三个都不是"功能没实现"，而是**实现了但会出事**。
这正是 02 存在的意义——01 看不见它们，03 做的时候才发现就晚了。
