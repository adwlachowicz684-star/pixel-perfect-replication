> **简单项当场给迁移后实现方案并修掉**，正好趁深挖解决 BUG。
> 自检：`python3 scripts/bug_triage.py ledger/bugs.md --gate`

| 编号 | 一句话 | 位置 | 类别 | 严重度 | 分诊 | 状态 |
|---|---|---|---|---|---|---|
| B-001 | 拖到空白被当错误，实为换栏移动通路 | DragService.cs:88 | B1 | P1 | 进批次 | 已完成 |
| B-002 | 名称校验 3 处不一致 | mod.rs:112 | B3 | P1 | 简单 | 已修（当场） |
| B-003 | 只加 +s 不加 +h | sys.rs:201 | B5 | — | 待确认 | 已确认非 BUG |

**类别**：B1 原版 BUG / B2 当前版 BUG / B3 审查发现的风险 / B4 迁移引入 / B5 存疑待确认
**严重度**：P0 阻断 / P1 严重 / P2 一般 / P3 轻微（数据不可逆损失额外打 `[险]`）

**简单项五条判据（全满足才当场修）**：
单文件内 · 不涉并发/数据格式/契约 · 有明确验证方式 · 不需要重构 · 不打断主线

**不登记的 BUG 修复 = 静默改需求。**

## 13. 功能对照表 `ledger/feature_matrix.md` ⭐

> **给「人」看的总账**（给项目组、给验收人、给后来接手的人）。
> 与第 1 份功能台账**互补不是替代**：台账管"挖全了没"，对照表管"每条怎么定的"。
> 自检：`python3 scripts/feature_matrix.py --check ledger/feature_matrix.md --gate`

| 编号 | 功能 | 原版 | 新版 | 处置 | 依据（证据卡/性质） | 状态 |
|---|---|---|---|---|---|---|
| 1 | 跨栏拖到空白=换栏移动 | ✅ | ✅ | **原样复刻** | E-012 设计意图 | 完成 |
| 4 | 启动弹更新提示 | ✅ | ❌ | **需要讨论** | 卡在哪 / 谁拍板 / 截止时间 / 超时默认 | 待拍板 |

**处置五选一**：原样复刻 / 考虑优化 / 架构性调整 / 需要讨论 / 不适用

**四条判据**（区分这五类，别混）：
1. 去掉它，体验或正确性会受损吗？会 → **原样复刻**
2. 换实现但行为不变吗？是 → **考虑优化**
3. 动的是模块边界而非单点实现吗？是 → **架构性调整**
4. 拿不到证据 / 需要业务裁决吗？是 → **需要讨论**

**❗「需要讨论」必须写全四栏**才算登记完成：
`卡在哪 / 谁拍板 / 截止时间 / 超时默认动作`
**超时默认按「原样复刻」执行**（保守优先：漏做是确定的功能缺失）。

**⚠️ 三种「不齐」要显式标记**：
`原版✅新版❌` = 缺口（是有意不迁移还是没做？）·
`原版❌新版✅` = 增强（记反向清单，**别在对齐时被误删**）·
**`原版✅新版❌` 却标「完成」是最危险的组合** —— 脚本会单独挑出来。

## 实施批次

```
第 0 批：数据风险（[险]，纯风险不掺功能）← 必须最先
         ├─ 含 P0/P1 的 [险] BUG（B1-B4 中涉及数据不可逆损失的）
第 1 批：[易] 小项（快速见效）
         ├─ 含"简单"分诊的 BUG（其实多数已在深挖时当场修掉）
第 2 批：某个完整子系统（如拖拽 35 项，必须整体做，不许拆散）
第 3-5 批：按模块推进
第 6 批：像素回归
```

**BUG 的批次归属**：
- 简单项 → **深挖时当场修**，不占批次
- `[险]` / P0 / P1 → 第 0 批（与数据风险同级，**会放大后续所有改动**）
- P2/P3 → 随所属模块批次
- B5 存疑 → 先确认，未确认前不进任何批次（等同 unknown）

**数据风险会放大后续所有改动**：每加一个功能就多一次读写，
底层有覆盖漏洞时，加的功能越多、丢得越快。
