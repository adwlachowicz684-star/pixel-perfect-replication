# 功能对照表 `ledger/feature_matrix.md`

> **一句话**：一张表回答四个问题——
> **原先有哪些功能？现在有哪些功能？每条怎么处置的？哪些还没定？**
>
> 这是给**人**看的总账（给项目组、给验收人、给后来接手的人），
> 与 `ledger/features.md`（给执行看的逐条台账）**互补，不是替代**：
> 台账管"挖全了没"，对照表管"每条怎么定的"。

自检：`python3 scripts/feature_matrix.py --check ledger/feature_matrix.md --gate`

## 二、五类处置（每行必填，不许空）

| 处置 | 含义 | 必须附什么 | 不附会怎样 |
|---|---|---|---|
| **原样复刻** | 行为、参数、文案、边界全照搬 | 证据卡 ID + 性质（设计意图 / 优秀实践） | 后人不知道为什么不能改，早晚被"优化"掉 |
| **考虑优化** | 换实现但**行为等价** | 新方案 + **边界行为如何等价**（错误文案、失败回退、极端输入） | 换方案最容易丢的，就是丑实现里藏着的边界处理 |
| **架构性调整** | 跨模块重组（统一入口/状态/错误/命名） | 重组前后对照 + 每个原入口的新落点 | 功能对齐了但更难用 |
| **需要讨论** | 卡住了 | **卡在哪 / 谁拍板 / 截止时间 / 超时默认动作** | **变成永久黑洞** |
| **不适用** | 平台或架构差异 | 差异说明 | 以后重新挖出来当新发现 |

### ⚠️ 四条判据（区分这五类，别混）

1. **去掉它，体验或正确性会受损吗？** 会 → 原样复刻
2. **换实现但行为不变吗？** 是 → 考虑优化
3. **动的是模块边界而非单点实现吗？** 是 → 架构性调整
4. **拿不到证据 / 需要业务裁决吗？** 是 → 需要讨论

> **它是不是比你现在想写的方案更好？** 是 → 原样复刻 + 推广（优秀实践 G-N）

## 三、❗"需要讨论"是最容易失控的一类

**一条"需讨论"项只有写全这四栏才算登记完成**：

```
| 4 | 启动弹更新提示 | ✅ | ❌ | 需要讨论 | 卡在哪：原版无日志，无法判断是否有人用
|   |                |   |    |          | 谁拍板：产品负责人
|   |                |   |    |          | 截止时间：2026-10-15
|   |                |   |    |          | 超时默认：按"原样复刻"执行（保守优先）
```

**⚠️ 超时默认动作必须写** —— 没有兜底，"讨论"就会无限期挂着，
最后在验收时变成一笔糊涂账。

**默认原则：超时按"原样复刻"执行**（保守优先）。
因为漏做是确定的功能缺失，而多做一个没人用的功能是低代价的。

**`discuss` 项未写全四栏 → 脚本判定为未处置，硬门禁阻断。**

## 四、三种"不齐"状态要显式标记

| 原版 | 新版 | 含义 | 必须说明 |
|---|---|---|---|
| ✅ | ❌ | **缺口** | 是"还没做"还是"有意不迁移"？**有意不迁移要写理由** |
| ❌ | ✅ | **增强** | 记入**反向清单（勿删）** —— 别在"对齐"时被误删 |
| ✅ | ✅ | 已对齐 | 处置四选一 |

**⚠️ "原版有新版无"且状态为"已完成"是最危险的组合** ——
说明被当成做完了，实际是丢了。脚本会单独挑出来。

## 五、与功能清单对账

`ledger/features.md` 里每条功能（1-N）**必须在对照表出现**，反过来也一样。
脚本会做双向差集：

```bash
python3 scripts/feature_matrix.py --check ledger/feature_matrix.md \
        --features ledger/features.md --gate
```

**对不上说明两条之一**：
- 挖到了但没定处置 → 补处置
- 定了处置但没进台账 → 补编号

## 六、状态

`待判` / `待做` / `进行中` / `完成` / `待拍板`（仅 discuss）/ `已裁定`（仅不适用）

**收工判据**：无 `待判`、无 `待拍板`、无"原版有新版无却标完成"的项。

---

## 七、给验收人看的三句话

1. 这张表是**决策记录**，不是进度表 —— 进度在台账里。
2. **"需要讨论"项必须有截止时间与超时默认动作**，否则不算登记完成。
3. **功能全对齐了但更难用** 是架构性调整最常见的失败模式 ——
   重组前后对照栏不许空。
